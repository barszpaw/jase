# VC1541 / SDI — ZX Spectrum 1541 Disk Interface

Research/planning doc for a new JASE peripheral: a hardware interface that lets
a ZX Spectrum talk to a Commodore 1541 disk drive over the IEC serial bus.
Real device: **SDI (Spectrum Disk Interface)**, hardware by Uroš Milan,
firmware by Geren Ivan, PCB by Mario Prato (KiCad, Rev 1.0). "VC1541" is the
German/Central-European branding of the Commodore 1541 — same drive.

Same spirit as `docs/SPECTRANEXT.md`: gather the facts now so implementation
can start quickly later, without re-deriving them from scratch.

## What's real vs. what's AI-reconstructed

This doc draws on two very different kinds of source, and they should not be
trusted equally:

- **Real, verified, ground truth**: the schematic image (`SDI_schemat.png`,
  straight out of KiCad), the real PCB Gerbers (`VC1541_v2.1.ZIP`, dated
  2025-03-24), and the real ROM dump (`SDI103J_ED3DC6CD.ROM` / `.h`, 4096
  bytes, CRC32 `0xED3DC6CD` — verified by recomputing it from the file).
- **AI-generated commentary** (a chat with another model on Arena, preserved
  in full at the bottom of this doc): port semantics, procedure labels, a
  "full disassembly", and hardware-improvement suggestions. The model was
  given the real ROM bytes and asked to disassemble them, so the *opcodes* in
  its listing are consistent with the real ROM — but the labels, comments,
  and claims about *why* a bit does what it does are the model's inference,
  not verified against real hardware. It explicitly hedges some of this
  itself ("prawdopodobnie", "musisz to przetestować").

**Two concrete corrections found by cross-checking the chat against the real
schematic** (do not trust the chat on these points):

1. **8255 Port B is `$BF`, not `$5F`.** The schematic's own port-map note
   (top right of `U10`) reads: `PA $9F`, `PB $BF`, `PC $DF`, `CONF $FF`. Every
   message in the Arena chat says Port B is `$5F` — wrong, probably a
   plausible-sounding guess the model never corrected itself on.
2. **The front-panel button (`SW1`) pulls the Spectrum's `RST` line, not
   `/NMI`.** The schematic shows `SW1` (`SW_Push`) wired to a trace labelled
   `RST`, which is also one of the labelled `P1` edge-connector pins (the
   Spectrum's real `/RESET` line) — there is no `/NMI` signal anywhere in
   this schematic. The chat repeatedly asserts "Naciśnięcie przycisku
   generuje /NMI" and builds the whole bootstrap story around an NMI vector;
   that part needs to be rethought (most likely: the ROM is entered via a
   normal full reset, and the ROMCS decode logic — or the ROM's own code at
   whatever address the Spectrum's ROM vectors to post-reset — is what gets
   control, not an NMI handler). **Not yet re-derived from the gate network
   in the schematic** — flagged here as a known-wrong claim to fix before
   writing any NMI-handling code, not yet replaced with a verified answer.

Everything else from the chat (IEC bit-banging approach via 8255 Port C,
overall memory map, general component list, the TCP-bridge architecture
proposal) is plausible and matches the schematic's visible structure, but
still unverified in detail — treat procedure names/addresses in the
disassembly as a first-pass hypothesis, not fact, until cross-checked against
assembling the `.asm` back to the exact `SDI103J_ED3DC6CD.ROM` bytes.

## How to run it: bridge + JASE

Two processes, started in this order (the bridge first — JASE's
`connectBridge()` dials out to it on startup and gives up if nothing's
listening yet).

**1. Start the bridge** (`tools/c64iec_fs/c64iec_fs_tcp.py`, GPLv3, its
own directory/license — see "Bridging to a real/virtual 1541" below
for why). Point `--basedir` at either a loose directory of `.prg`
files or directly at a `.d64` image (auto-detected by the `.d64`
suffix):

```sh
python3 tools/c64iec_fs/c64iec_fs_tcp.py \
    --tcp-port 9101 \
    --basedir /path/to/AceofAces_SDI.d64
```

Leave this running in its own terminal — it logs every `OPEN`/`READ`/
`WRITE` it handles, which is the easiest way to confirm JASE's requests
are actually reaching it. `--devid N` (default 8) matches the device
number the ROM's `*DRIVE`/`LISTEN`/`TALK` commands address.

**2. Start JASE**, pointing `--sdi-bridge` at that same host:port. The
real ROM needs the 128K machine type and its own 4KB dump:

```sh
./jase --machine 128k --sdi --sdi-rom docs/VC1541/SDI103J_ED3DC6CD.ROM \
    --sdi-bridge 127.0.0.1:9101
```

`--sdi-rom` implies `--sdi`; `--sdi-bridge` also implies `--sdi` — so
in practice you only ever need to pass the last two flags. Watch
JASE's own stdout for `SDI: bridge connected to <host>:<port>` to
confirm the dial-out succeeded; `SDI: bridge connect to ... failed` means
the bridge wasn't listening yet (start it first) or the port's wrong.

**3. Activate SDI from BASIC**: type `RANDOMIZE USR 16000` and press
ENTER — see "USR 16000 activation" below for exactly what this does
(and does NOT do — no banner, just `BORDER 1: PAPER 1: INK 7: CLS`) and
why spelling it out letter-by-letter through a naive keyboard-typing
tool doesn't work (BASIC keywords are single keystrokes in the real
keyboard-to-token system, not spelled text). From there, disk commands
all start with `*` (`*CAT` to list the disk, `*LOAD"name"`, `*SAVE
"name"`, etc. — see `SDI_Command.pdf` under `docs/VC1541/web/.../rom/
SDI/` for the full command reference).

**Headless/scripted testing** (no real window, used throughout this
doc's own verification): `SDL_VIDEODRIVER=dummy SDL_AUDIODRIVER=dummy`
before the `./jase` command, plus `--debug-port 9999` to drive it over
the line-based debug protocol (`OUT`/`PORT`/`STEP`/`CONT`/`BREAK`/
`MEM`/`POKE`/`REGS`/`TYPE`/`PRESSKEYS`/`SCREENSHOT`/... — see
`debugserver.cpp` for the exact command set) instead of a keyboard and
screen.

## Hardware summary (from the real schematic)

**Memory map:**
- ROM: 4KB (`U8`, a 2764 EPROM) at `$3000–$3FFF`. `CE` (chip enable) is
  generated by the address-decode gate network (`U2A/U2B`, `U3A`,
  `U4A–U4D`, `U5A/U5B`, `U6A–U6D` — a mix of 74LS20/27/30/260/02) from
  `A15/A14/A13/A12/A11/A10`, `M1`, `MREQ`, `IORQ`. `ROMCS` also lights `D1`
  (LED) through `Q1` (BC547) and `U1E` (74LS06).

**I/O (8255 PPI, `U10`), per the schematic's own port-map label:**
| Port | Address | Pins |
|---|---|---|
| PA | `$9F` | PA0–PA7 |
| PB | `$BF` | PB0–PB7 |
| PC | `$DF` | PC0–PC7 |
| Control/CONF | `$FF` | — |

The `CS`/`RD`/`WR` of the 8255 and the PPI decode come from the same gate
network as `ROMCS` (`CE` signal), gated with `IORQ`.

**IEC bus:**
- `PC0` → `U1A` (74LS06, open-collector) → `ATN` (pull-ups `R5`/`R6`, 1kΩ, to
  VCC)
- `PC1` (`PC1` net also routed back to the EPROM's `CE`/program-enable side —
  worth re-checking exactly what `PC1` does both for IEC and for ROM control)
- → `U1B` → `CLK` (pull-ups `R8`/`R9`)
- → `U1C` → `DAT`
- `U1F` (74LS06) is explicitly marked `spare` — unused gate.
- `J1`, a DIN-6 connector labelled "IEC PORT / 1541 Disk Drive", with pins
  per the schematic: `2`→ATN, `4`→CLK, `5`→DAT, `3`→RES, plus GND. (Cross-
  check against a real Commodore serial-bus pinout reference before wiring
  anything physical — DIN-6 pin numbering conventions vary by source.)

**Power:** `U9` (LM7805, TO-220) regulates Spectrum's +9V edge-connector rail
down to +5V, with the usual decoupling caps (`C1–C7`).

**Reset:** `SW1` (push button) pulls the `RST` line (see correction #2 above
— this is the Spectrum's real `/RESET`, not an NMI).

**Edge connector (`P1`, `SPECTRUM_EDGE-28x2`):** full Z80 bus exposed —
`A0–A15`, `D0–D7`, `M1`, `MREQ`, `IORQ`, `RD`, `WR`, `RST`, plus `+9V`/`GND`.
Nothing exotic; same bus JASE already exposes to its other `Peripheral`s
(DivIDE, Multiface, ZiFi).

## Proposed software architecture (from the chat, matches JASE's existing conventions)

The chat's proposal lines up with how JASE already does things (`Peripheral`
base class, `ZiFi`'s own TCP-bridge-to-a-companion-process pattern — see
`src/ZiFi.h`/`src/ZiFi.cpp` and `tools/virtual_esp01/`): don't bit-bang IEC
timing inside JASE itself, bridge it over TCP to a separate process (Python
or C++) that either emulates a 1541 in software or drives a real Arduino +
physical IEC bus. The existing open-source project `c64-fdemu` already does
exactly the Arduino-bridge half of this (`C64 → IEC → Arduino → USB-serial →
PC → Python 1541 emulation`) and conveniently has a Python-side 1541
emulator already — reusable almost as-is for the PC end of this bridge, with
JASE's `SDI_Periphery` talking the same wire protocol `virtual_esp01`-style.

Sketch (from the chat, needs adapting to JASE's real `Peripheral` interface,
not the placeholder names below):

```cpp
class IECInterface {
public:
    virtual ~IECInterface() = default;
    virtual void setATN(bool state) = 0;
    virtual void setCLK(bool state) = 0;
    virtual void setDATA(bool state) = 0;
    virtual bool getDATA() = 0;
    virtual bool getCLK() = 0;
    virtual void delayMicroseconds(uint32_t us) = 0;
    virtual void onLineChange() = 0; // bridge reports a line change
};

class TCPBridgeClient : public IECInterface { /* ... */ };

class SDI_Periphery : public Peripheral {
    std::unique_ptr<IECInterface> iec;
    uint8_t portC_latch = 0xFF;
    const uint8_t* rom = nullptr; // SDI103J_ED3DC6CD_ROM
    bool rom_enabled = true;
    // in()/out() decode $9F/$BF/$DF/$FF (8255) same as ZiFi decodes its own ports
    // mem read for $3000-$3FFF when rom_enabled
};
```

Proposed wire protocol for the bridge (1 command byte + 1 data byte):
- `0x01 xx` — SET_LINES (`xx`: b0=DATA, b1=CLK, b2=ATN)
- `0x02` — GET_LINES (bridge replies with current line state)
- `0x03 nn` — DELAY_US (bridge can simulate real IEC timing)
- `0x04` — RESET

## Implementation status

**Done** — `src/SDI.h`/`src/SDI.cpp`, a `Peripheral` subclass, same shape as
`DivIde`/`Multiface`. `--sdi` / `--sdi-rom PATH` on the command line (off by
default, same convention as `--divide`/`--multiface1`).

- 8255 port decode: `(port & 0xFF & 0x9F) == 0x9F` selects the chip,
  `(port >> 5) & 3` picks PA(0)/PB(1)/PC(2)/CTRL(3) — derived with high
  confidence from the schematic's own published addresses sharing that bit
  pattern (not guessed), verified live via the debug protocol (`OUT`/`PORT`
  on `$9F`/`$BF`/`$DF`/`$FF` all round-trip correctly and independently; an
  unrelated port like `$1F` is correctly left unclaimed).
- ROM paging: constructed an 8K `MemoryMap::Bank` where the lower 4K
  ($2000–$2FFF) is snapshotted from whatever's *already* mapped at page 1
  (always the other half of a read-only ROM pair on every machine type —
  see `setupInitialPaging()` — so copying it once is safe, no write ever
  needs to land there instead) and the upper 4K ($3000–$3FFF) is the real
  SDI ROM. Page-in trigger is the **same first-pass hypothesis** flagged
  above as unverified in detail (M1 opcode fetch landing in $3000–$3FFF
  while not already active, DivIde/Multiface-style — not the chat's wrong
  NMI story), but it's no longer *just* a hypothesis: see the verification
  below.
- **Verified against the real ROM, not just built**: forced PC into
  `$3000` via the debug protocol's `--pc`/`--poke` test harness (same
  mechanism `main.cpp` documents for exercising a peripheral with no
  keyboard/window-manager path). The real ROM's own
  `L3000_PORT_DF_CLEAR_BIT2` routine (`IN A,($DF)` / `AND $FB` / `OUT
  ($DF),A` / a short delay loop / `RET`) then ran for real: `SDI`'s
  internal `portC_` latch changed from its `0xFF` default to exactly
  `0xFB` — bit 2 cleared, precisely matching `AND $FB`. That's direct
  evidence the ROM paged in correctly, executed real SDI code (not
  garbage) against the emulated 8255, and then `RET`-ed itself back out of
  the $3000–$3FFF window, at which point `onInstructionFetch()` correctly
  paged it back out again (confirmed `active=0` and the original page-1
  content restored afterward) — the full in→run→out cycle working
  end-to-end on the first real ROM it was tried against.

**ROMCS trigger boundary — narrowed from $3000-$3FFF to $3C00-$3FFF,
confirmed by four independent lines of evidence** (not just the
earlier single-test hypothesis above):

1. The schematic's own ROMCS gate-network inputs list exactly 6
   address lines (`A10-A15`), which decode a 1024-byte granularity —
   i.e. $3C00-$3FFF, not the full 4K.
2. The real ROM's own bytes have a 527-byte `0xFF` filler run from
   $39F1-$3BFF immediately *before* the first real code at $3C00 (five
   harmless `DI` opcodes as address-decode-slop margin, then real code
   starting at $3C05). $3000-$39F0 is real code too (confirmed by
   `BUGS.txt`'s own byte-offset patches landing in there), but it's
   only ever reached via internal `CALL`s from the $3C00+ entry code —
   never a direct M1 landing.
3. The ROM's own official README (`SDIv103J.TXT`) says verbatim:
   "Intercepts 128 ROM at $3C04 and performs a USR 0." A fresh
   disassembly (via the `z80dis` Python package, cross-checked byte-
   for-byte against the real ROM file, not the Arena chat's listing —
   see below) of $3C00-$3C11 matches exactly: `DI`×5 (padding) / `XOR
   A` / `OUT ($1FFD),A` / `LD B,$7F` / `LD A,$10` / `OUT ($7FFD),A` /
   `RST 0` — i.e. force 48K-compatible ROM/RAM paging, then restart.
   $3C18 onward (reached on a *separate* later M1 fetch, not a
   fall-through from `RST 0`) patches the stack slot pointed to by
   `ERR_SP` ($5C3D) to $3C5F, so a future BASIC syntax error (e.g.
   typing an unrecognized `*COMMAND`) redirects into SDI's own code
   instead of the normal "Nonsense in BASIC" — the real mechanism
   behind `*COMMAND`/`*CAT`, no NMI or separate hardware hook needed.
4. **Empirically confirmed** by booting JASE's own real, unmodified
   128K ROM (`/usr/share/fusex/128-0.rom`/`128-1.rom`, no SDI loaded at
   all) with a debug-protocol breakpoint at `$3C04` and a real
   `RESET`: it hits immediately and repeatedly, because $3C04 is part
   of the stock 128K menu's own keyboard-scan wait loop (`LD
   BC,$BFFE`/`IN A,(C)`/`BIT 0,A`/`JR Z,..`) — continuously executed
   from power-on, before a user ever sees the 128K menu. With SDI
   loaded, the *same* boot (now intercepted) shows `7FFD` forced to
   $10-then-$17 (48K ROM1 selected) within milliseconds, `active`
   correctly dropping back to 0 once PC leaves $3000-$3FFF, and a
   stable, non-crashed PC afterward — the narrowed trigger works
   end-to-end against the real ROM, not just in isolation.

**Cross-checking the Arena AI chat's own disassembly against the real
ROM bytes — a concrete example of why it's flagged as unverified.**
The chat independently guessed $3C5F was significant (calling it
`L3C5F_BOOTSTRAP_INIT`), which turned out to be directionally right —
but its *specific* claim, a standalone routine at $3C5F that prints
the DOS banner and installs hooks, does not match the real bytes. The
real banner text ("SPECTRUM DISK INTERFACE"/"DOS V1.03J") was
confirmed, byte-for-byte, to live at $32B1 (`rom.find(b"SPECTRUM DISK
INTERFACE")` against the real ROM file), and the real banner-print
loop is at $3C46-$3C50 — called from the $3C00 entry's own
continuation, not from a separate $3C5F routine. $3C5F in the real ROM
is used purely as a 16-bit *data value* (the vector written into the
`ERR_SP`-pointed stack slot), never a label the chat's imagined code
actually reaches. An earlier pass of the same chat also mislabeled the
port-$DF bit-twiddling routines by one slot (claiming $3006 is
`PORT_DF_SET_BIT2` when the real bytes show $300D is, with $3006-$300C
actually being a shared delay+`RET` tail the chat didn't account for).
Net: useful as a source of *hypotheses* about structure and purpose,
unreliable on specific addresses/labels — verify every claim against
the real ROM bytes with a disassembler before relying on it, same
discipline as the two corrections already documented above.

**PC0-7 bit mapping — confirmed, not guessed.** The rendered schematic PNG
wasn't legible enough on its own (wires cross too much at that resolution);
resolved by asking Pawel to check the actual KiCad schematic directly:

| Bit | Mask | Role |
|---|---|---|
| PC0 | 0x01 | ATN output (via U1A) — always driven by us, we're the controller |
| PC1 | 0x02 | separate, non-IEC signal (not understood yet, unused here) |
| PC2 | 0x04 | CLK output (via U1B) |
| PC3 | 0x08 | DAT output (via U1C) |
| PC4,PC5 | 0x10,0x20 | unused for IEC |
| PC6 | 0x40 | CLK read-back (tied to U1B's own output net, pulled up 1K) |
| PC7 | 0x80 | DAT read-back (tied to U1C's own output net) |

This 0-3-output/4-7-input split is exactly what 8255 mode 0 allows (each
nibble of Port C independently directioned) — a good independent sanity
check that the mapping is right, not a coincidence.

**IEC protocol facts — verified against a primary source, not memory.**
Before writing any bit-level timing logic, fetched and read the actual
ASCII timing diagrams from Commodore's own IEC Serial Bus Manual
(commodore.ca's reproduction — [raw text](https://www.commodore.ca/wp-content/uploads/2018/11/Commodore-IEC-Serial-Bus-Manual-C64-Plus4.txt)),
cross-checked against [pagetable.com's independent writeup](https://www.pagetable.com/201).
Both agree:
- All lines active-low (pulled low = logical 1/asserted).
- CLK is always generated by the active TALKER; **the RISING edge of CLK
  is when the DATA bit is valid** and gets sampled — this is the one
  load-bearing fact the whole byte-clocker below is built on.
- ATN: controller pulls it low: all devices must respond (pull DATA low)
  within 1000µs or it's a "device not present" error.
- End of a byte: listener pulls DATA low within 1000µs to acknowledge.
- EOI (last byte): sender delays starting the next bit by ≥200µs instead
  of the normal handshake timing; listener acks by holding DATA low
  ≥60-80µs then releasing.

**IEC byte-level decode — implemented and verified.** `SDI::clockBit()`
is a generic rising-edge-of-CLK shifter used in two phases:
- **Under ATN**: we're always the sender (we're the controller), clocked
  off our own driven CLK (PC2). Verified by hand-driving the exact real
  bit sequence for `LISTEN device 8` (`0x28`) through the debug protocol's
  `OUT DF ..` — `SDI`'s `lastByte_` came back as exactly `0x28`.
- **Post-ATN data phase**: direction depends on which PRIMARY address
  (not a secondary/channel byte) was last clocked under ATN — LISTEN
  (`0x20-0x3E`) means we keep sending (`IecRole::WeAreTalker`); TALK
  (`0x40-0x5E`) means the device sends and we receive
  (`IecRole::WeAreListener`); UNLISTEN/UNTALK (`0x3F`/`0x5F`) clear the
  role. Verified: after clocking LISTEN `0x28` under ATN, releasing ATN,
  then clocking a data byte with ATN low, `role` correctly stayed
  `weTalk` and the byte decoded correctly (LSB-first reconstruction
  confirmed bit-for-bit against what was actually sent).
- The `WeAreListener` direction is plumbed into `in()` (clocks off
  read-back CLK-in/PC6 instead of our own driven CLK) but can't produce
  real events yet — `clkLine()`/`datLine()` only ever reflect our OWN
  drive right now (no external device or bridge connected), so there's
  nothing to clock off until the TCP bridge exists.

**EOI and channel semantics — implemented and verified.**
- **EOI**: approximated via elapsed `onInstructionFetch()` calls (fires
  every Z80 instruction regardless of which peripheral is paged in) since
  the last bit clocked, rather than real microseconds — the real
  threshold is ≥200µs (~700 T-states @ 3.5MHz); `kIdleInstructionsForEoi`
  (40) is a rough per-instruction stand-in, explicitly flagged as an
  approximation in the code, not a verified exact count. Verified with
  the CPU stopped and `STEP` driving `onInstructionFetch()` deterministically
  (debug-protocol `OUT` alone doesn't execute instructions, so testing
  this needed real single-stepping, unlike everything else so far):
  clocking a byte with zero steps in between came back `eoi=0`; clocking
  one after 45 explicit `STEP`s came back `eoi=1`.
- **Channel/file semantics**: a secondary address under ATN is now
  decoded as OPEN (`0x60-0x6F`), CLOSE (`0xE0-0xEF`), or the plain
  channel-select KERNAL LOAD/SAVE convention (`0xF0-0xFF`) uses without a
  separate OPEN — standard, long-published CBM serial-bus facts, not
  specific to any one codebase. Data-phase bytes after an OPEN accumulate
  as a filename, committed to `filenames_[channel]` the moment
  UNLISTEN/UNTALK ends the exchange; after a plain-select, they're left
  as the just-finished LOAD/SAVE payload for inspection (`SDI FILES`)
  until the next secondary byte starts a new session. Verified
  end-to-end via the debug protocol: `LISTEN 8` → `OPEN channel 2`
  (`0x62`) → release ATN → clock `"TEST"` byte-by-byte → `SDI FILES`
  showed `bufLen=4 buf=TEST` mid-transfer → `UNLISTEN` → `SDI FILES`
  then showed `filenames=2:TEST,`, confirming the full OPEN→filename→
  commit path works.

**TCP bridge — implemented and verified end-to-end against a real test
disk.** `SDI::connectBridge()` (`--sdi-bridge HOST:PORT`) is a plain
blocking socket to `tools/c64iec_fs/c64iec_fs_tcp.py` — blocking, not
ZiFi's non-blocking `pump()`, matching the real Arduino-side
`IECSerialFile`'s own blocking-read design (see the licensing section
below for why reading that for its wire format is fine but copying it
isn't). OPEN/CLOSE/SAVE fire straight from `finalizeSession()` since the
whole payload is already decoded by then; LOAD's `R,<ch>,<size>` request
fires earlier, from `onSecondaryByte()` (while still under ATN), since
the bytes need to be ready before the Z80 starts polling for them —
landing in `pendingLoadData_`/`pendingLoadEoi_`, inspectable via `SDI
BRIDGE`.

**LOAD encoder — implemented and verified end-to-end against the real
bridge+disk.** `advanceLoadEncoder()` is the inverse of `clockBit()`: a
state machine (`Idle` → `WaitDataReady` → `BitSetup` → `BitValid` →
`WaitAck` → next bit/byte) that drives `deviceClk_`/`deviceDat_`
(exposed through `in()`'s PC6/PC7 synthesis when `role==WeAreListener`)
one half-step per `in()` poll, mirroring the Z80's own ready/ack
handshake on its side of the shared DATA line. Chunk refills
(`fetchMoreLoadData()`) fire transparently mid-stream when
`pendingLoadData_` runs out and `pendingLoadEoi_` isn't set yet.

Two real bugs were found and fixed while building and testing this
(both predate the encoder — it just was the first thing to actually
exercise the paths they live in):

- **PC6/PC7 read-back polarity.** PC6/PC7 are wired *directly* to the
  bus node (no inverting buffer, unlike PC0/2/3's output path through
  U1A/B/C) — the old code exposed them with the same polarity as the
  output bits, backwards for these two. Fixed in `in()`'s port-C case.
- **`clockBit()`'s CLK edge direction was backwards**, in every call
  site. The verified protocol fact is "CLK asserted → released is the
  sample point" (a 0→1 electrical transition given this project's
  "bit set = asserted" convention through the inverters); the original
  trigger fired on the opposite transition. This had passed every
  earlier single-byte test (`LISTEN 0x28`, `OPEN`+filename `TEST`)
  only because those hand-written test scripts held DATA constant
  across both halves of each bit, which reads the same value on either
  edge direction and completely masks the bug. It only surfaced once
  the LOAD encoder's `BitSetup`/`BitValid` states (which vary DATA
  correctly across the two phases, matching real hardware) exposed the
  mismatch. Fixed in both `out()`'s two `clockBit()` calls and the
  self-decode call in `in()`.

A third, structural issue surfaced only once multi-byte LOAD sequences
were actually driven through the encoder: the real IEC protocol
(re-verified against both primary sources — the Commodore manual's own
ASCII timing diagram and pagetable.com's independent step-by-step
writeup) inserts an **extra CLK release between every two bytes**
("talker ready to send"), electrically identical to a real per-bit
sample release and impossible to distinguish by edge direction alone.
The fix: the self-decode path in `in()` now decides off the encoder's
own state (`stateBefore == BitValid`) rather than a raw CLK edge, since
the state machine authoritatively knows which release is which. This
also fixed a related stale-exposure bug at the last bit of each byte
(`BitValid → WaitAck`), where the old post-call state check exposed
`datLine()` instead of the just-sampled bit — a real-hardware-visible
bug, not just a self-decode artifact, since it's the same bits a real
Z80 would be polling.

Verified against the real `AceofAces_SDI.d64` (not a synthetic file),
driven through the full `LISTEN`→`OPEN channel 0`→filename `*`→
`UNLISTEN`→`TALK`→plain-select→release-ATN sequence via the debug
protocol, acting as the "virtual Z80 listener" (releasing/asserting its
own DATA bit at the right points in each `WaitDataReady`/`WaitAck`
window): 260 bytes driven through the encoder, decoded via the
self-decode path into `SDI`'s own `dataBuf_`, matched byte-for-byte
against the bridge's own `pendingLoadData_` content at each chunk fetch
— including the exact 254-byte chunk-refetch boundary, where a byte
count or state-machine desync would have shown up immediately.
(Confirming this needed the debug protocol's `SDI`/`SDI BRIDGE` reply
buffers bumped from 340-400 chars to 1536 — the originals silently
truncated a full 254-byte chunk's hex-escaped preview well before the
boundary, which first looked like a decode mismatch and wasn't.)

Still deliberately not implemented: talker-side EOI signaling for a
LOAD's actual last byte (the encoder currently treats it like any
other byte, per the EOI approximation discussion above — the consumer
side, i.e. byte-level decode of an incoming EOI flag, already works;
only the encoder's own "delay before the final byte" signal is
missing).

**SAVE-direction listener ack — implemented and verified.** The
`WeAreTalker` direction (OPEN filenames, SAVE payload) used to only
self-decode the Z80's own CLK/DATA writes without ever driving a
"virtual listener" ack back onto the DATA line, unlike the LOAD
encoder's `WaitAck` state in reverse — meaning a real Z80 ROM that
actually waits for the addressed device to acknowledge each byte
(per the same primary-source protocol used above) would have stalled
against this emulation. Fixed by giving `SDI` a `listenerDat_` bit
(exposed through `in()`'s PC7 synthesis whenever `role==WeAreTalker`,
the mirror image of the LOAD path's `deviceDat_`) that plays the
addressed device's own listener role: released ("ready for data")
once the sender's inter-byte "ready to send" CLK release arrives,
asserted ("byte accepted") the instant `clockBit()` completes a byte —
the exact reverse of `advanceLoadEncoder()`'s own
`WaitDataReady`/`WaitAck` handshake.

This also resolved the matching receive-side half of the "extra
ready-to-send CLK release between bytes" ambiguity (see the LOAD
encoder section above): `clockBit()` itself now tracks a shared
`awaitingInterByteRelease_` flag, set the instant a byte completes (or
a fresh ATN/data-phase session starts, alongside its existing
`bitCount_`/`shiftByte_` reset in `out()`) and consumed — without
counting as a bit — the next time a CLK edge arrives. Since both of
`out()`'s `clockBit()` call sites (ATN-phase command bytes and
WeAreTalker data-phase bytes) now share this one flag, both benefit
from the fix, not just the WeAreTalker path the ack driver itself
targets.

Verified end-to-end via the debug protocol, acting as a protocol-
faithful sender that honours the new ack handshake (releasing CLK for
"ready to send", waiting for `listenerDat_` to release before clocking
8 bits, then waiting for it to re-assert before the next byte): a
`LISTEN 8` → `OPEN channel 3` → 8-character filename (`DISKFILE`,
crossing 8 byte boundaries) → `UNLISTEN` sequence came back with
`filenames=3:DISKFILE` — exact, byte-for-byte, with every single
ack wait resolving instead of timing out. A second run, `LISTEN 8` →
plain-select channel 5 → a 16-byte payload (crossing 16 byte
boundaries, including non-printable bytes `0x00/0xFF/0x7F/0xAA/...` to
exercise the hex-escaped debug readout) → `UNLISTEN`, came back with
`buf=\x00\x01\x02\xff\x7fABCDE\xaaU\x00\xfe\x10\x99` — again exact.
Both runs would have produced garbage from the second byte onward had
either the ack handshake or the byte-boundary fix been wrong, since a
real sender only proceeds past the inter-byte release once it observes
the listener's ack. Talker-side EOI signalling for an actual SAVE's
last byte (the ATN-phase/WeAreTalker byte stream has no notion of
"this is the final byte" yet, mirroring the LOAD encoder's own
still-missing talker-side EOI noted above) remains unbuilt.

Verified against the REAL disk images under `docs/VC1541/web/.../disk/`
(`AceofAces_SDI.d64`), not a synthetic test file: forced the exact IEC
bit sequence for `LISTEN 8` → `OPEN channel 0` with filename `*` →
`UNLISTEN` through the debug protocol, with `c64iec_fs_tcp.py` actually
mounting the real `.d64` and listening on a real socket — `SDI BRIDGE`
came back `lastReply=OK`, meaning the real bridge process resolved the
wildcard against the real disk's directory (to `ACE OF ACES`, confirmed
by also testing the bridge standalone) and opened it. `CLOSE` verified
the same way.

**D64 disk image support in the bridge (not from upstream — fresh
code)**: `c64iec_fs_tcp.py --basedir some.d64` now parses the image
directly (standard, long-public D64 layout: 35 tracks, directory chain
from track 18/sector 1, each entry's own track/sector data chain) and
serves its contents exactly like a loose-file directory, in on-disk
order. This is what makes the real SDI disk images usable without a
separate extraction step — and matches a documented real workflow, not
a guess: `docs/VC1541/web/.../rom/SDI/SDIv103J.TXT` (the real ROM's own
README) describes `*COM "CD/directory/d64image.d64"` mounting a D64 on
a real SD2IEC exactly this way. Verified standalone (before wiring the
C++ side to it) against both real test images: `LIST` showed all 4
files with correct sizes, `OPEN *` resolved to the first file, `READ`
returned the exact same bytes an independent manual chain-walk of the
same image produced.

## USR 16000 activation, the real boot banner, and DEVICE NOT PRESENT

**`$3E80` (decimal 16000) confirmed as the real, documented activation
entry point — matches a NEW primary source, not disassembly guessing.**
`SDI_Command.pdf` (the hardware/firmware authors' own magazine article,
"Moj Mikro" 1986 №07, pages 32-33+23 — a far more authoritative source
than the Arena AI chat) says verbatim: *"What you need to remember is
to type RANDOMIZE USR 16000 before starting to work with SDI, preferably
immediately after turning on the computer. The same instruction must
also be the first in the program that uses SDI commands... Apart from
the connection to SDI, the command also executes `BORDER 1: PAPER 1:
INK 7: CLS` on first execution."* $3E80 = 16000 decimal exactly, and
it's the known internal `JP $3C18` target found earlier (see the
ROMCS boundary section above) — independently confirmed correct from
two completely different angles now.

**Verified live**, bypassing the real Sinclair BASIC keyword-entry
system entirely (see "why not just TYPE it" below): stopped the CPU at
the idle loop's own `RET` (`$1600`), overwrote the return address on
the stack with `$3E80` via the debug protocol's `POKE`/`MEM`, then
`STEP`-ped — landed exactly on `$3E80`, which (correctly, since $3E80
falls in the $3C00-$3FFF ROMCS window) paged SDI in and ran `JP
$3C18` → `active=1`. Continuing: it called out to the stock ROM's own
CHAN-OPEN (`$1601`) and a ROM-internal routine around `$0E5C`/`$0D6B`
(pageOut correctly fired while in stock-ROM territory, pageIn fired
again on return — the paging mechanism handles this "call out, call
back in" pattern correctly), then a 100-iteration loop through `$3E2B`
(`PUSH AF`/`EI`/`RST 16`/`DI`/`POP AF`/`RET` — the real, standard
Spectrum "print one character to the current channel" wrapper).

**Correction to a correction: the banner DOES print — confirmed by an
actual on-screen run, which is the one kind of evidence that beats
everything else in this doc.** Pawel ran `RANDOMIZE USR 16000` for
real (proper keyboard, real GUI window, not the debug-protocol
shortcut) and got exactly: `BORDER 1`/`PAPER 1` (blue), `INK 7`
(white/bright-grey) — matching `SDI_Command.pdf` precisely — **and**
"SPECTRUM DISK INTERFACE" / "DOS V1.03J" / the two authors' names
printed on screen, which `SDI_Command.pdf` never mentions. So the
earlier write-up here was wrong to conclude "no banner exists" — the
PDF is a real, authoritative source but not an *exhaustive* one; it
documents the color/CLS side effect and doesn't happen to mention the
text. The Arena AI chat's specific claim (a `L3C5F_BOOTSTRAP_INIT`
routine) is still wrong on placement (confirmed earlier: the real
banner text lives at $32B1, printed via the loop at $3C46-$3C50, not
from $3C5F) — but its underlying premise, "a banner prints," was right
after all. Net lesson, consistent with this doc's whole approach: an
unreliable source being wrong on specifics doesn't mean its central
claim is wrong too, any more than a reliable source being right on one
point makes it exhaustive — check the actual, real, running system
before writing either down as settled.

Following directly from the same real run: the screen then filled with
repeated `DEVICE NOT PRESENT` errors and a `scroll?` prompt — see
"DEVICE NOT PRESENT — found and fixed" below for the real bug this
exposed and the fix. Screen state after a correctly-working activation
is expected to settle to the blue/blue/white boot screen with no
errors, not the DEVICE NOT PRESENT wall seen before that fix.

## DEVICE NOT PRESENT — found and fixed

Running the real ROM for real, with the real bridge connected and
confirmed accepting the TCP connection (its own log showed "Client
connected -- treating as adapter reset" repeatedly), still produced a
screen full of `DEVICE NOT PRESENT` errors. Root cause: **nothing in
`SDI.cpp` ever simulated the device side of the ATN handshake.** The
verified protocol fact (see the protocol-facts section above) is that
every device on the bus must respond to ATN by pulling DATA low within
1000µs, or the controller reports exactly this error — a real
open-collector line, so any device pulling it reads as asserted for
*everyone*, independent of what the controller itself last drove there.
Every earlier hand-written test script in this doc's own verification
history manually drove BOTH sides (the controller's writes via `OUT`,
*and* the "device is ready"/"device acks" signals a real listener would
produce) — which is exactly why ATN/LISTEN/OPEN decode checked out
perfectly in isolation, while the real, unscripted ROM saw nothing but
its own loopback on the DATA read-back and correctly, honestly reported
no device present.

Fixed in `in()`'s port-C case (`src/SDI.cpp`): when `atnLine()` is
asserted and a bridge is actually connected (`bridgeFd_ >= 0`), the
DATA read-back (PC7) now reads asserted unconditionally, simulating
"yes, device 8 exists and is responding" — gated on a real bridge being
attached so that running `--sdi` with no `--sdi-bridge` still honestly
reports no device, rather than pretending to work and then failing
later at `OPEN`/`READ` instead. Not yet re-verified against a second
real on-screen run after this fix (the fix followed directly from the
screenshot, same session) — next thing to confirm.

**Why not just `TYPE "RANDOMIZE USR 16000"` through the keyboard
sim?** Tried first, and it's a real methodology gap worth recording:
JASE's debug-protocol `TYPE` command spells text out via individual
PC-keyboard-style letter keypresses. On a real Spectrum, BASIC
keywords are NOT entered by spelling them out — in "K" (keyword)
cursor mode, a single unshifted letter keypress (e.g. "R") produces an
entire reserved word (its own meaning depends on cursor mode), not the
literal letter. Spelling "R-A-N-D-O-M-I-Z-E" through `TYPE` typed the
keyword for the first letter, then kept going in whatever mode followed,
literally spelling "andomize" as if it were a variable name — confirmed
by the exact error produced: `2 Variable not found, 0:1`. A second
pitfall found along the way: `PRESSKEYS`/`TYPE` both call
`MinZX::pressKeys()`, which unconditionally clears the whole queued-key
buffer (`autoTypeSeq_.clear()`) — calling `TYPE` then a separate
`PRESSKEYS RETURN` wipes out the just-typed text before any of it is
delivered, so RETURN arrives alone on an empty line. Properly testing
through the keyboard requires either keyword-aware single-keystroke
entry (matching the real K/L/C/E cursor-mode system `*CAT`'s own
"extended mode + 9" entry already hints at) or driving it the way this
session did — directly via the debug protocol, bypassing the keyboard
simulation's current ASCII-letter-spelling limitation.

**Resolved: `PRESSKEYS` works fine once the real keyword-entry key
sequence is used instead of spelling words out.** Verified against the
real, verified keyword→key table (ZX Spectrum skill's own
`keyboard-tokens.md`, not guessed): `T` alone in K-mode (start of
line) is the `RAND` token (shown as `RANDOMIZE`); `USR` is the
Extended-mode (CAPS SHIFT+SYMBOL SHIFT together, then a key alone —
not SYMBOL SHIFT+key) meaning of `L`. The working sequence, sent as one
`PRESSKEYS` call against a real, visible (non-headless) JASE window
with `--sdi --sdi-rom --sdi-bridge` all connected:

```
PRESSKEYS T,SHIFT+ALT,L,1,6,0,0,0,RETURN
```

(`T`→`RANDOMIZE `, `SHIFT+ALT`→toggle Extended mode, `L` alone→`USR`,
then the digits for `16000`, then the real ENTER key — not the "Y"
key's own `RETURN` keyword, a different, easy-to-confuse thing.)
Confirmed working two ways at once: visually, `BORDER` turned blue on
the real window (Pawel confirmed it live), and over the debug protocol,
`STATE` read back `border=1` — matching `BORDER 1` from
`SDI_Command.pdf` exactly — with `SDI`'s own status also showing a real
decoded IEC byte (`fromAtn=1`), not a failed/empty call. This replaces
the `SETREG`-based direct-jump workaround for any test that should go
through BASIC's own command line for real, since it's no longer
necessary — `SETREG` remains useful for isolating protocol-level
behavior without the keyboard/BASIC layer in the way (e.g. the
DEVICE NOT PRESENT fix verification above).

## `*CAT`/`*LOAD` investigation — real findings, genuinely open questions

Pawel's own live testing (real keyboard, real visible window) surfaced that
`*CAT` hangs the keyboard, and the same turned out to be true for
`*LOAD "ace of aces"`. This section documents what the subsequent
investigation actually established — some of it solid, some of it still
unresolved — rather than a finished fix. Picked up again from "zrób tak by
było sprawnie i skutecznie" (make it efficient and effective) and "może
trzeba emulować 8522?" (maybe need to emulate a 6522?).

**Methodology: `SDI_IOTRACE`, a port-access logger.** Added to
`src/SDI.cpp`/`SDI.h`: every `IN`/`OUT` to all four 8255 registers
(`PA`/`PB`/`PC`/`CONF`) gets logged to stderr with the current PC, e.g.
`IOTRACE pc=336f IN DF -> 7a (atn=0 clkIn=0 datIn=1 role=0)`. `lastPC_`
(new member, updated every `onInstructionFetch()`) makes the PC
available inside `in()`/`out()`, which don't otherwise see it. Started
as a `#ifdef SDI_IOTRACE` compile-time flag (needed a separate rebuild
to turn on); turned into a runtime toggle after Pawel asked for it to
be reachable without rebuilding — now a `--debug-iotrace` command-line
flag, or live via the debug protocol (`SDI IOTRACE ON`/`SDI IOTRACE
OFF`/bare `SDI IOTRACE` to just report the current state). Worth
keeping for future low-level IEC debugging rather than a one-off
throwaway.

**Confirmed: Port A and Port B are never touched.** Across a full `*LOAD`
attempt (1.26 million trace lines, the machine spinning in a hang for most
of it), `CONF` (`$FF`) is written exactly twice at startup (value `$98` —
Group A/PC-upper = input, Group B/PC-lower = output, matching the already-
documented PC0-3 output / PC4-7 input split) and Port A/B are **never**
accessed at all. Rules out Pawel's "maybe need a 6522" hypothesis directly:
whatever SDI's firmware does for `*CAT`/`*LOAD`, it does entirely through
Port C, the same single 8255 register everything else in this doc already
covers — no second I/O chip, no parallel side-channel.

**Confirmed: the real per-bit receive routine (`$3138`) matches
`advanceLoadEncoder()`'s states exactly.** Traced live via repeated
`SETREG`/debug-protocol `OUT` nudges on the CLK bit, watching real CPU
execution advance one step at a time (not a synthetic test): `$3151`
(`IN;AND $40;JR Z,...`) waits for CLK **asserted** — matches `BitSetup`'s
own action. `$3177` (`IN;ADD A,A;JP P,...`) waits for CLK **released** —
the sample point, matches `BitValid`'s own action, and the same `ADD A,A`
instruction captures the DATA bit into carry (original bit7) while testing
CLK via the result's sign flag (original bit6) — confirming DATA readback
really is the bit content and CLK readback really is the handshake signal,
exactly as modeled. `$3182` then waits for CLK asserted again (next bit's
`BitSetup`), and this repeats 8 times (`$3188`/`DEC(HL)`/`JR NZ,$3177`),
assembling the byte LSB-first via 8 `RR(HL)` rotations. This is strong,
live-verified confirmation that the *mechanism* `advanceLoadEncoder()`
implements is the right one for `*LOAD`'s actual data phase — once a byte
transfer is actually under way, nothing about the bit-level protocol needs
to change.

**Confirmed: `$336F` ("Talk-Attention Turn Around", the device-must-grab-
CLK handshake documented earlier in this file) is reached during
`RANDOMIZE USR 16000`'s own bootstrap, not specifically during `*LOAD` or
`*CAT`.** Traced via the exact `IOTRACE` sequence `pc=3356`(release ATN)→
`pc=3000`(release CLK)→ the `$3026`/`$302d` debounce-read pair repeating
forever — this is unambiguously `$335D`'s own call chain (`$3366 CALL
$3356`, `$3369 CALL $3000`), not `$3138`'s (which would show a `CALL
$301D`/DAT-release step first). `IFF1=0` throughout (interrupts disabled)
— so this is a genuine, permanent CPU-level hang once hit, not something
that could resolve itself given enough wall-clock time; it requires an
actual external response.

**Open, unresolved contradiction: `border=1` is not proof `USR 16000`
fully completed.** `BORDER 1`/`PAPER 1`/`INK 7` get set early in the
bootstrap and persist regardless of what happens later — so "`STATE`
shows `border=1`" (checked and reported as a success signal earlier in
this doc) does *not* actually prove the rest of the bootstrap, including
`$335D`/`$336F`, ran to completion. Separately, an *earlier* test in this
same session (a second `RANDOMIZE USR 16000` call, with the `$5CB0`
banner-skip flag already set from a first call) *did* return cleanly to
the idle loop with a real decoded IEC byte, no hang. Whether every call
path through `$3C04`'s bootstrap reaches `$335D`, or only some (e.g. the
banner-skip branch jumping to `$3C52` might skip it, where the normal
first-call branch doesn't) is **not yet established** — this needs a
side-by-side trace of a genuine first call vs. a second call, which
wasn't done before time ran out on this investigation.

**Still completely unlocated: how the filename gets sent to the drive.**
Throughout the entire `*LOAD "ace of aces"` attempt, `SDI BRIDGE` showed
`lastReply=` (empty) — `bridgeOpen()` was never called. Nothing in this
investigation found where/how `*LOAD`'s filename argument gets
transmitted over IEC. It's not going through the ATN-phase
LISTEN+secondary-byte+filename-bytes+UNLISTEN sequence this file's own
earlier "Channel/file semantics" section describes and verified (that
mechanism was tested via hand-scripted Python, never confirmed against
what the real ROM's own `*LOAD`/`*SAVE`/`*CAT` command handlers actually
do) — `lastByte_`/`fromAtn_` never updated to anything new during the
whole attempt. There is presumably a symmetric "send byte" counterpart to
`$3138`'s receive routine somewhere in the `$30xx`-`$34xx` region, not yet
located. Until this is found, fixing the CLK handshake alone would not be
enough to make `*LOAD`/`*CAT` work end-to-end — the bridge would never
even be told what to open.

**Net assessment:** this turned out to be substantially more than a
two-point handshake fix. What's solid: the per-bit receive mechanism is
confirmed correct, Port A/B are confirmed irrelevant, and the IOTRACE
tooling now exists for whoever continues this. What's still open: the
exact conditions under which `$335D`/`$336F` get reached (or don't),
and — the bigger piece — the entire filename-send path, which hasn't
been traced at all yet.

## Filename-send mechanism — found (via Ghidra cross-check)

Continuing the "still completely unlocated" item above, using an
independent Z80 disassembly (Ghidra 12.3, built from source and run
headless — see the note on `SDI103J_ED3DC6CD_ghidra_disasm.txt`, a local,
untracked reference file) cross-checked byte-for-byte against `z80dis`.
Where the two independent decoders agreed and the byte alignment checked
out against a raw hex dump (several ROM regions are reached only via
`CALL`/`JP`, not sequential fall-through, so a naive linear sweep
misaligns them — caught and corrected by re-decoding from the actual call
target address each time, e.g. `$3078`, `$3350`, `$5c9c`), the following is
now established directly from the real ROM's bytes, not guessed:

**The ATN-phase address machinery, fully mapped:**
- `$3075`/`$3078` — two entry points into the same routine, differing only
  in which bit they OR into the computed device byte before falling into
  shared continuation code: `$3075` ORs `$40` (TALK range `$40-$5E`),
  `$3078` ORs `$20` (LISTEN range `$20-$3E`). Both store the result into a
  one-byte "next byte to send" buffer at `$5c95`, special-case the `$3F`
  UNLISTEN sentinel, and fall into `$30a2`.
- `$30a2` — **assert ATN**, assert CLK, release DAT, settle delay, then
  send the buffered byte (via `$30d4`). This is the primary address byte
  (device + LISTEN/TALK direction).
- `$30ab` — assert CLK, release DAT, settle delay, send buffered byte —
  identical to `$30a2` minus the ATN-assert step. Used for a second byte
  sent while ATN stays asserted (the secondary/channel address byte).
- `$30d4` — the actual bit-bang sender (8 bits, LSB-first, matches
  `advanceLoadEncoder()`'s receive-side convention mirrored for sending):
  release DAT, check the listener's DAT-readback for an error abort (`JP
  M,$3036`), release CLK, then the per-bit loop at `$30f7`-`$3135`
  (assert CLK + set DAT to the bit value, release CLK as the sample
  point, release DAT, re-assert CLK — one iteration per bit, `DJNZ`
  eight times). Only ever reached from inside this same address-sending
  machinery (`$3089`/`$30b9`/`$30ca`) — confirmed by grepping every
  `CALL`/`JP 0x30d4` in the disassembly.
- `$3350` — send byte (continuation, via `$30ab`) then **release ATN
  only**, return. Used when we (the computer) remain the active sender
  for whatever data phase follows — i.e. after a LISTEN+OPEN, when we're
  about to stream bytes *to* the drive ourselves.
- `$335d` — send byte (continuation) then do the **full
  Talk-Attention-Turn-Around handoff**: assert DAT, release ATN, release
  CLK, then the `$336F` wait-for-new-talker's-CLK loop documented above.
  Used when control is handed to the *other* side as new talker — e.g.
  `$3e9e: LD A,$6f (OPEN channel 15) / CALL $335d`, immediately after a
  `CALL $3075` that sends a TALK address — a "TALK device, open channel
  15, then wait for the drive to start talking" sequence (reading the
  drive's response/status channel).

**The actual filename-send loop — found.** `$3481`-`$3491`:
```
3481: LD A,(0x5c9c)      ; filename length
3484: LD HL,(0x5c9e)     ; filename buffer pointer
3487: LD B,A
3488: LD A,(HL)          ; loop: next char
3489: PUSH HL / PUSH BC
348b: CALL 0x30bc        ; send it (pipelined, see below)
348e: POP BC / POP HL
3490: INC HL
3491: DJNZ 0x3488
```
`$30bc` is a small *pipelined* sender wrapper (`PUSH`/`CALL $30d4`/`POP`,
then `LD (0x5c95),A` *after* the call): it physically transmits whatever
was already queued in the `$5c95` buffer, then queues the byte just
passed in `A` as the *next* one to go out on the following call — a
one-byte transmit pipeline, not a bug. A second, structurally similar
loop exists at `$34c8`-`$34f0`, iterating a `(start-pointer $5c98,
end-pointer $5c9a)` pair instead of `(pointer $5c9e, length $5c9c)` —
likely a sibling command's own data-phase send (not yet confirmed which).

**Where `$5c9c`/`$5c9e` get filled in** — `$3ec7`-`$3ed7`: captures a
length into `$5c9c` and a buffer address into `$5c9e` via a call into the
host BASIC ROM (`RST $30` / the `$1601`-family routines used throughout
this ROM for calling back into the Spectrum's own ROM) — consistent with
parsing the quoted filename argument out of the typed `*L "name"` command
line.

**A confirmed red herring, flagged so it doesn't get re-chased:** `$5c9c`
is reused for something completely unrelated earlier in the same command's
execution — a relocated-code accessor (ROM `$344f`-`$345f`, 17 bytes,
copied via `LDIR` into RAM at `$5c9c` and entered via `JP $5c9c`) for the
SDI's own onboard paged auxiliary RAM, using ports `$9F` (page select) and
`$BF` (data read) — the *only* place in the whole ROM Port A/B actually
get touched, and it has nothing to do with IEC or the filename. The two
uses don't collide at runtime (the relocated-code use finishes and
returns before `$5c9c` gets overwritten with the filename length later in
the same command), but it's a genuine instance of the firmware reusing one
RAM address for two unrelated purposes at different times — worth keeping
in mind if tracing this further.

**Which command is `L` — traced and confirmed.** `$33c7` turned out *not*
to be the command dispatcher itself (it's a different, unrelated-to-IEC
subroutine — see the paged-RAM red herring below). The real `*`-command
entry is a patched Spectrum system hook: typing `*` is detected at
`$3c91` (`LD HL,(0x5c5d)` — `CH ADD` — `DEC HL`/`CP 0x2a`, checking the
*previous* character consumed was `*`), which jumps to `$39a5`, a generic
keyword matcher — structurally the same algorithm the real Spectrum ROM
uses for its own BASIC keyword table (`RST $18`/`$20` to read/advance,
`$3cbe` to uppercase-fold, bit7-marks-last-char convention).

The real command table lives at `$35aa`, decoded entry-by-entry by
replicating the matcher's own skip rule (scan for a bare `$80` byte,
skip 3 more trailer bytes, repeat):

| table addr | stored text | full word (first letter consumed earlier) | handler |
|---|---|---|---|
| `$35aa` | `AVE` | SAVE | `$3c4c` |
| `$35b2` | `OAD` | **LOAD** | **`$3c56`** |
| `$35b9` | `ERIFY` | VERIFY | `$3c4d` |
| `$35c2` | `ERGE` | MERGE | `$3ccf` |
| `$35ce` | `NITIALIZE` | INITIALIZE | `$3d56` |
| `$35db` | `ALIDATE` | VALIDATE | `$3dd0` |
| `$35ee` | `ENAME` | RENAME | `$3dd2` |
| `$360b` | `OMMAND` | COMMAND | `$3d43` |
| `$3615` | `AT` | CAT | `$3c44` |
| `$361b` | `RIVE` | DRIVE | `$3eff` |

Every entry is missing its own first letter — confirming the first
letter is matched separately, *before* this table is even consulted, and
explaining directly why Pawel's own `*L "ace of aces"` (bare single
letter, no more following it before the space/quote) works exactly like
`*LOAD` would: the matcher's "last character" fallback (`$39d0`: try the
plain letter, then try it OR'd with `$80`) accepts an early delimiter as
a valid stop, i.e. this parser accepts the shortest unambiguous prefix.

**LOAD's full call chain, traced end to end:**
1. Table match → `$3c56`, which does two `CALL`s in sequence (realigned
   from the stored handler address, which lands mid-instruction on a
   naive linear decode — same "entry point offset by N bytes into a
   shared tail" pattern seen everywhere else in this ROM):
   - `CALL $3f33` — parses the quoted argument following `*L` via `RST
     $30` (the real Spectrum ROM's own `BC-SPACES` workspace allocator,
     called the same convention-respecting way the rest of this ROM
     calls back into the host ROM elsewhere, e.g. `$1601`), records the
     buffer pointer into `$5c9e` and length into `$5c9c`, appends a CR
     terminator, switches the 8255 back from whatever mode to `$98`
     (confirmed IEC mode), sets `(0x5c9d) = 0x6f`, falls into `$3996`.
   - `CALL $3f47` — separately injects a **literal, hardcoded `"UI-\r"`
     string** via `$3ebd` (a generic "copy this fixed constant into a
     fresh RST-$30 buffer, same $5c9e/$5c9c convention" helper), also
     through `$3996`. `UI-` is a real, documented Commodore 1541 DOS
     command (forces standard/non-fast serial-bus speed) — this means a
     real `*LOAD` sends **two separate OPEN+send sequences**, not one:
     the filename, and then this housekeeping command.
2. `$3996` (shared by both): appends the CR terminator at the just-
   recorded buffer's end, reconfigures the 8255 to `$98`, sets
   `(0x5c9d)=0x6f`, jumps into **`$345e`**.
3. `$345e` is the real identity of what last session's notes called
   "one of (at least) four structurally similar OPEN+send blocks" (what
   was labeled `$3463` there is this same code — just the continuation
   past `$345e`'s own `OR A`/`RET M` early-out check, not a separate
   command). From here the already-mapped machinery runs: `$3078`
   (LISTEN+devnum), `$3350` (send secondary, release ATN, keep talking),
   the `$3481`-`$3491` per-character send loop reading `$5c9c`/`$5c9e`,
   then `$3060` (UNLISTEN).

**Still fuzzy, flagged rather than guessed at:** `$3463`'s own secondary-
address computation is `(0x5c9d) | 0xf0`, which with `(5c9d)=0x6f` from
both LOAD call sites works out to `0xff` — outside the normal
`$60`-`$6F` OPEN-channel secondary-address range this file documents
elsewhere. Either `0xff` carries different meaning in this specific
context, or something mutates `(0x5c9d)` between the filename pass and
the `"UI-"` pass that wasn't found. Not resolved — don't take `0xff` as
a confirmed real bus byte without checking this further.

**A confirmed non-finding, worth remembering so it doesn't get
re-chased:** `$33c7` (which looked promising as "the" dispatch table
last session, given its nearby `LDIR`/`CALL 0x3e6e` character-reading

relocated-code trick (`$344f`→RAM `$5c9c`, entered via `JP 0x5c9c`) as
the filename-length/pointer variables, but for an unrelated purpose
(the `CALL 0x3e6e`/`CP 0x45` check tests for a specific single
character, not a general letter dispatch). Not pursued further since
`$39a5`/`$35aa` turned out to be the real, confirmed answer.

**Still open:**
- JASE's own `SDI.cpp`/bridge only implements the *receive* direction

- The `0xff` secondary-address puzzle above.
- SAVE/VERIFY/CAT's own call chains (`$3c4c`/`$3c4d`/`$3c44`) haven't been

## First implementation attempt — two real bugs fixed, one genuinely open

Picked up from "zaplanuj i wdróż działania by to działało" (plan and
implement so it actually works). Two concrete, live-tested fixes landed
in `SDI.h`/`SDI.cpp`; a third issue was found but not yet resolved.

**Fix 1 — the `$336F` Talk-Attention-Turn-Around handshake, done
properly this time.** `advanceLoadEncoder()`'s `Idle` state used to
double as both "just took over the bus, holding CLK" (the one-shot
grab $3142/$3145 is waiting for) and "parked, nothing to send" (the
bridge had no data) — the same overload that caused the earlier
reverted "permanent assert" experiment. Split into two states:
`TalkTurnaround` (one-shot: assert CLK for exactly one `in()` poll,
then unconditionally move to `WaitDataReady` or `Idle` next poll) and
a now-genuinely-parked `Idle`. `onSecondaryByte()` always starts at
`TalkTurnaround`, data or not.

**Fix 2 — `onSecondaryByte()` was only kicking off the LOAD encoder for
the `$F0`-`$FF` secondary form.** Live-tested finding: the real ROM's
`$3e8f` (called early in `*LOAD`'s own flow, reading the drive's
response on the command channel) sends a TALK primary followed by
secondary `$6F` — the classic `$60`-`$6F` **OPEN** form, not `$F0`-
`$FF`. `onSecondaryByte()` had the LOAD-kickoff logic nested inside the
`PlainSelect` branch only, so `Open`+`WeAreListener` got no bus-grab at
all — confirmed live: stuck at PC `$3025`, return address `$336F` on
the stack, `iecRole_` correctly `WeAreListener` but `loadEncState_`
still sitting at its default `Idle`. Moved the kickoff out to fire for
any non-`Close` secondary while `WeAreListener`, regardless of which
form it is.

**Verified improvement, not yet full success.** With both fixes, one
full live run (`RANDOMIZE USR 16000` → `*L "ace of aces"`, real bridge,
real `AceofAces_SDI.d64`) completed *without hanging* — the ROM printed
the real **"SEARCHING FOR ace of aces"** banner (confirmed on an actual
screenshot) and returned cleanly to BASIC (`IFF1=1`, SDI paged out).
That's new: the original bug always hung identically. But the bridge's
own log stayed empty the whole time — `bridgeOpen()` was never actually
called — so the file still isn't being opened end to end yet.

**A third, deeper issue found, not fixed.** A second identical attempt
(this time with `SDI_IOTRACE` on) hung again, at the exact same
`$3025`/`$336F` signature, but on a *different* byte than Fix 2
addressed: `$3e8f`'s call into `$3075` (meant to just OR `$40` into the
computed device number and send it as the TALK primary) turns out to
share its tail with the `$3078` LISTEN entry via a byte-level overlap —
and that shared tail (`$307a` onward) has its own conditional branch on
bit 7 of `(0x5c94)`, a persistent flag this decoder doesn't track, that
can route through an *entirely different*, not-yet-understood
side-channel (rotating bits out of `(0x5c96)` via repeated `CALL
$30d4` calls) instead of just sending the primary address bitbanged
from `in()`/the usual path. Live-reconstructed byte sent in this run:
`$9F` — not in any of LISTEN/TALK/UNLISTEN/UNTALK/Open/Close/
PlainSelect's ranges, so `onSecondaryByte()` correctly does nothing
with it, but nothing upstream sent a valid primary either, so
`iecRole_` never leaves `None` and the real ROM spins forever waiting
for a response nobody gives. Whether this side-channel is routinely
hit (making the whole command inherently flaky depending on
`(0x5c94)`'s value at the time) or only hit under specific prior
state isn't established — the first (successful) run and the second
(hung) run used the *identical* key sequence against the same ROM, so
this looks state-dependent rather than deterministic either way.

**Net assessment:** real progress (the single confirmed permanent hang
is fixed; the command now visibly executes further, including a real,
correct on-screen message), but not yet a reliable, working `*LOAD` —
there's at least one more genuinely unresolved branch in the real
ROM's own command-channel logic standing between here and a file
actually opening on the bridge.

## Bridging to a real/virtual 1541 — `c64-fdemu`

Pawel's plan: reuse `fox20io/c64-fdemu` (https://github.com/fox20io/c64-fdemu)
— specifically its `src/fileserver/c64iec_fs.py`, which already does real
file-serving (wildcard resolution, directory listing, chunked reads with
progress reporting — seen working live against a real C64 in a screenshot)
— by swapping its current USB-serial-to-an-Arduino transport for a plain TCP
socket, "resztę architektury zostawiam tobie" (architecture otherwise left
to me), with the one constraint that JASE's side follows the existing
`Peripheral` convention.

**Licensing: both `c64-fdemu` and the `IECDevice` library it bundles
(`src/iec2usb/lib/IECDevice-main/`) are GPLv3** (confirmed by reading their
`LICENSE` files directly). Per this project's established practice all
session (`ZiFi`, `tools/virtual_esp01`, the `Gopher`/`Tnfs` clients were all
written clean-room specifically to keep GPL code out of JASE's own,
MIT-licensed tree) — **no code from either gets copied into JASE.** What
*is* fair game, and what the rest of this section is built from: reading
`IECSerialFile.cpp`/`.h` (the Arduino-side class whose job is exactly
"forward file ops to a host computer over serial", the thing being replaced
with "forward over TCP") purely for the **wire protocol it already uses** —
a fact about an interoperability format, not a copyrightable expression,
same category as the pico-spec/fusex port-number facts already reused
elsewhere in this project. Pawel's own copy of `c64iec_fs.py`, patched to
listen on TCP, can be run entirely outside the JASE repo as his own separate
GPL tool — nothing about that requires vendoring GPL code into JASE at all.

**The real wire protocol** (read directly from `IECSerialFile.cpp`, not
guessed — `CHUNK_SIZE` is 128, from `IECSerialAdapterConfig.h`):

| Direction | Format | Meaning |
|---|---|---|
| → host | `O,<ch_hex>,<name>\n` | open `name` on channel `ch` |
| ← host | `OK...\n` or anything else | open succeeded / failed |
| → host | `R,<ch_hex>,<chunksize>\n` | request up to `chunksize` bytes |
| ← host | `<M\|L\|E>,<n>\n` + `n` raw bytes | `M`=more follows, `L`=last chunk (EOI), `E`=error/EOF (no bytes follow) |
| → host | `W,<ch_hex>,<n>,<E\|C>\n` + `n` raw bytes | write `n` bytes, `E`=this is the last write (EOI), `C`=more follow |
| ← host | `OK...\n` or anything else | write accepted / rejected |
| → host | `C,<ch_hex>\n` | close channel `ch` |
| ← host | (one line, ignored) | ack |

**What JASE's side actually has to do, in three layers** (clarifying the
"architecture" the chat sketched, now that the real library's shape is
known): `IECSerialFile`/`IECFileDevice` on the Arduino do NOT implement raw
electrical IEC bit-banging themselves — that's `IECBusHandler`/`IECDevice`,
a layer below, driving real pins with microsecond timing. JASE has no real
pins to drive and doesn't need that layer at all. What JASE's `SDI`
peripheral *does* need, because the real ROM bit-bangs IEC electrically
through the emulated 8255 Port C, is the **middle** layer — the genuinely
public, not-GPL-specific Commodore IEC bus protocol (ATN assertion,
TALK/LISTEN device addressing, OPEN/CLOSE/byte-level read-write handshake,
EOI) — decoded from Port C's bit transitions, clean-room, the same way
`ZiFi` decodes its own ZX-Uno bit-level register writes rather than copying
pico-spec's GPL code for it. Once that layer turns a 74LS06-level bit
sequence into a clean "channel N opened with name X" / "byte arrived on
channel N" event, the **outer** layer is just forwarding that event over
TCP using the wire format above — the part `IECSerialFile` already shows
the shape of, and the part Pawel's own patched `c64iec_fs.py` (external,
GPL, his) answers.

### **SDI (Spectrum Disk Interface) – Specyfikacja dla Peripheria / MinZX_SDL**


#### **1. Cel implementacji**

Emulacja

urządzenie w tablicy peryferiów. Ma działać zarówno ze stockowym ROM-em (`SDI103J_ED3DC6CD_ROM`), jak i z nowym firmwarem pisanym przez użytkownika.


#### **2. Memory Map**

- **ROM**: 4096 bajtów, mapowany na zakres **`0x3000 – 0x3FFF`**
- Gdy ROM jest włączony → całkowicie zasłania RAM Spectrum w tym zakresie (read zwraca bajt z ROM-u).
- Zapis do `0x3000-0x3FFF` powinien być ignorowany (ROM nie jest zapisywalny).
- **Sterowanie ROM-em**:
- Port **`0xDF`**, bit 2
- `bit 2 == 0` → ROM włączony
- `bit 2 == 1` → ROM wyłączony (widoczny normalny RAM Spectrum)
- Procedura z ROM-u: `L3000_PORT_DF_CLEAR_BIT2` robi `AND $FB` na porcie `$DF`.


#### **3. I/O Ports (najważniejsze)**

| Port | Typ | Nazwa w disassembly | Opis |
|---|---|---|---|
| 0xDF | R/W | PORT_PC | Główny port– IEC + sterowanie ROM-em + latch |
| 0xFF | W | — | 8255 Control Register– zwykle pisane wartością0x80(Mode 0, wszystkie porty wyjściowe) |
| 0x9F | R/W | — | Dostęp do Port A lub B 8255 (partial decode) |
| 0x5F | R/W | — | Dostęp do Port A lub B 8255 (partial decode) |

**Szczegóły portu `0xDF` (PORT_PC)**:

- Bit 2 – ROM control (0 = enabled)
- Pozostałe bity używane do bit-bangingu IEC (DATA, CLK, ATN)
- Kod ROM-u wykonuje operacje:
- `in a,(0xdf)`
- `and $fb` / `or $04`
- `srl c` + operacje na carry (IEC_SET_DATA_FROM_CARRY)
- `out (0xdf),a`

- Przycisk na kartridżu pociąga linię **/NMI** w dół.
- Wywołuje procedurę **`0x3C5F`** (`L3C5F_BOOTSTRAP_INIT`) znajdującą się w ROM-ie.
- Co robi bootstrap:
- Włącza ROM (czyści bit 2 w porcie `$DF`)
- Wyświetla baner (`SPECTRUM DISK INTERFACE`, `DOS V1.03J`)
- Instaluje własny hook komend BASIC-a pod adresem **`$5C5B`** (lub okolicznym – patrz `NEW_COMMAND_HOOK`)
- Inicjalizuje 8255 (`out (0xff), 0x80`)
- Ustawia stan IEC
- Wraca z NMI


#### **5. Sygnały CPU i magistrala**

- Pełne podłączenie do magistrali Z80:

- `/MREQ`, `/IORQ`, `/RD`, `/WR`, `/M1`

każdego 74LS-a – wystarczy poprawne zachowanie portów i mapowania 
pamięci.


#### **6. IEC (Commodore Serial Bus)**

jest realizowany w assemblerze Z80 z precyzyjnymi opóźnieniami.
- W emulatorze zalecane jest stworzenie **wirtualnego IEC Bus** (podobnie jak w Vice lub Hoxs64), do którego SDI i emulowana stacja 1541 mogą się podłączać.

   MIT license, confirmed before using it). Covers Mode 0/1/2 and Port C
   Bit-Set/Reset faithfully; only Mode 0 is live-verified (SDI's own real
   control byte, 0x98, live-traced), Mode 1/2 are "matches MAME's logic",
   not independently confirmed. Sanity-tested standalone (port read/write,
   Port C callback wiring, BSR) before anything else was built on it.

2. **`SDI_8255`** — the real board's I/O-decode + ROM/ROMCS hardware layer,
   gate-verified against Pawel's own schematic reading (truth tables for
   U3A/U4A/U4B's port-select NAND/NOR network and U5A/U2A/U5B/U2B/U6x's
   ROMCS/CE latch), **not** inferred from the ROM alone this time. Key findings:
   - I/O select matches the already-known `$9F/$BF/$DF/$FF` ports exactly,
     now derived from the real gate network instead of assumed.
   - ROMCS/CE really is a **latch** (confirmed via Pawel's truth tables, not
     a guess): a narrow SET condition (M1 fetch in `$3C00-$3FFF`) latches a
     BROAD sustain condition (any memory read anywhere in `$0000-$3FFF`, no
     A13 check) — meaning the EPROM overrides the *entire* lower 16K while
     latched, not just the 4K window the old SDI.cpp assumed.
   - The EPROM (2764, U8) only has A0-A11 wired from the Z80 bus — A12 comes
     from Port C bit 1 (PC1) instead (confirmed from the schematic, resolving
     the long-standing "PC1 — not yet understood" comment from the old code).
     Its 4K content therefore **mirrors** across the whole latched 16K
     window. Modelled by mirroring the active 4K bank into both 8K
     `MemoryMap` pages, not a single 4K slice. Second EPROM bank (PC1=1) is
     documented (per the SDI manual) as free user space, not alternate
     firmware, and nothing in the real ROM's traced execution ever toggles
     PC1 — modelled as erased-EPROM 0xFF.
   - Live-confirmed: `USR 16000` activation does reach and run inside this
     mirrored window (PC lands and executes sensible code there), and the
     ROM's own `DI x5` entry sequence pre-empts the one real risk the
     broadened mapping introduces (the `$0038` interrupt vector also falling
     inside the now-latched range) by disabling interrupts before anything
     could fetch through it.
   - The latch's own RESET condition isn't visible in the schematic excerpt
     seen so far — modelled as "M1 fetch outside `$0000-$3FFF`" (DivIde/
     Multiface's existing convention), explicitly flagged as an inference.

3. **`IIecDevice` / `IecBridgeClient`** — the bridge-communication layer,
   split out as its own interface + implementation (same shape as
   `IAySound`/`AyPsg`) specifically so the TCP bridge can later be swapped for
   a native 1541 emulation without any caller changing. `IecBridgeClient`
   reuses the exact wire protocol the old SDI.cpp's `bridge*` methods already
   proved out (O/R/W/C framed messages, read from fox20io/c64-fdemu's
   `IECSerialFile.cpp` — GPLv3, not copied, same "interoperability-format
   fact" reasoning as this project's other wire-protocol reuses).
   **End-to-end tested against the real `c64iec_fs_tcp.py` bridge**: connect,
   open a channel, read 128 bytes, close — all succeeded live, not just unit
   -tested in isolation.

4. **`IecBus` / `IecDeviceEmulator`** — the IEC protocol layer, and the part
   that took the most iteration. First attempt (`IecProtocolDecoder`) tied
   "us as receiver" and "us as sender" directly to a raw Port C byte in one
   class; this is what led to the periodic-pulse hack below and was replaced.

   **Byte-level receive algorithm and its real timing constants — 200us
   CLK-wait before declaring EOI, 80us EOI-ack pulse — read directly from
   fox20io/c64-fdemu's `IECBusHandler.cpp` (`receiveIECByte()`/
   `transmitIECByte()`), not approximated the way the original SDI.cpp had
   to.** This independently CONFIRMED several facts this project had already
   derived the hard way from the real SDI ROM: CLK's rising edge (asserted→
   released) is the valid-data moment, bits are LSB-first, asserted DAT=bit 0/
   released DAT=bit 1, and ~200us is a real hardware EOI threshold, not a
   guess. Per Pawel's explicit direction, timing is measured in **Z80
   T-states**, not wall-clock — `Peripheral::onInstructionFetch()`'s
   signature gained a `tstates` parameter (MinZX's own frame-relative
   counter) specifically for this, threaded through DivIde/Multiface/
   SDI_8255 as a no-op for anyone who doesn't need it.

   `IecBus` is the shared, wired-AND (open-collector) bus abstraction: the
   controller (SDI_8255/the Z80) and the device (`IecDeviceEmulator`) each
   drive their own view of CLK/DAT and both read the *resolved* line state,
   instead of one side reading the other's raw output directly — the same
   way a real multi-drop bus works, and the reason a real, symmetric talker
   implementation finally has somewhere clean to live.

   **Receive direction (ATN addressing, OPEN/CLOSE, WeAreListener data
   phase) is implemented and was confirmed working** before the current
   blocker was hit — `IECBUS` (a new debug-protocol command, deliberately
   non-stopping so it can be polled without freezing the Z80's own T-state
   clock, unlike a GDB breakpoint/watchpoint would) showed the idle-offer
   cycle and bus state live without issue.

   **Transmit direction (us driving CLK+DATA) is NOT properly implemented.**
   Live-tracing hit a real ROM routine (`$3142`-`$318c` in the dump's own
   addressing) that is the Z80's *own* "receive a byte" loop (mirroring
   `receiveIECByte`, just in Z80 asm) — but reached as part of the `$30D4`
   sender's error-recovery path, **without ATN ever being asserted first**.
   This is some kind of pre-ATN device-status probe this project has never
   seen run against real hardware, so what it actually wants is unknown.

   **Two guesses were tried and both failed to resolve it cleanly:**
   - A periodic CLK-in pulse (pure electrical toggle, no byte semantics) —
     got PC further than before (into the actual 8-bit sample loop) but
     never completed cleanly; the pulse's own period wasn't synchronized
     with the controller's polling, so bits sampled inconsistently.
   - A periodic "idle offer" (a real, correctly-timed 8-bit transmit of a
     placeholder 0x00 byte, repeating while the bus is idle) — same problem,
     different symptom: PC got even further (into the real sample loop
     proper) but still never resolved, just kept retrying.
   - **Both were reverted.** Pawel's own diagnosis of the pattern driving
     this investigation ("decode Z80, stub, see what's next") was correct —
     neither guess was grounded in a confirmed fact about what this specific
     probe wants, both were "try something, see if the ROM looks happier."
   - With the stub fully removed (bus genuinely silent, nothing asserted),
     the ROM's own retry **does** progress further on the very first pass
     after activation (new, previously-unseen addresses, interrupts
     re-enabled) than it ever did with either guess running — but then
     cycles back into the exact same `$3151`/`$11b0`-area retry loop this
     project has been looking at since the very start of this whole SDI
     investigation, and does not resolve on its own either. So the loop
     is NOT simply a bounded, self-resolving timeout the way `$3151`'s own
     local D-counter is — something in the larger retry structure still
     depends on a response this project hasn't correctly modelled.

**Where this leaves things:** the architecture (I8255 → SDI_8255 → IecBus/
IecDeviceEmulator → IIecDevice) is sound and each layer below the transmit
direction is independently verified, not just assumed. The actual gap is
narrow and specific: a real, protocol-correct talker implementation for
whatever this pre-ATN probe wants — not a wider architectural problem. The
right next step, explicitly NOT started yet, is almost certainly to stop
inferring from this ROM's own disassembly in isolation and instead check
whether a REAL Commodore 1541 (or the Arduino reference's own device-side
code) ever gets probed this same way before ATN, which would settle what a
correct response looks like instead of guessing another stub.
