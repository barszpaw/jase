# VC1541 / SDI — ZX Spectrum 1541 Disk Interface

Research/planning doc for a new JASE peripheral: a hardware interface that lets
a ZX Spectrum talk to a Commodore 1541 disk drive over the IEC serial bus.
Real device: **SDI (Spectrum Disk Interface)**, hardware by Uroš Milan,
firmware by Geren Ivan, PCB by Mario Prato (KiCad, Rev 1.0). "VC1541" is the
German/Central-European branding of the Commodore 1541 — same drive.

Same spirit as `docs/SPECTRANEXT.md`: gather the facts now so implementation
can start quickly later, without re-deriving them from scratch.

## What's real vs. what's AI-reconstructed

This doc draws on two very different kinds of source, and they should not be
trusted equally:

- **Real, verified, ground truth**: the schematic image (`SDI_schemat.png`,
  straight out of KiCad), the real PCB Gerbers (`VC1541_v2.1.ZIP`, dated
  2025-03-24), and the real ROM dump (`SDI103J_ED3DC6CD.ROM` / `.h`, 4096
  bytes, CRC32 `0xED3DC6CD` — verified by recomputing it from the file).
- **AI-generated commentary** (a chat with another model on Arena, preserved
  in full at the bottom of this doc): port semantics, procedure labels, a
  "full disassembly", and hardware-improvement suggestions. The model was
  given the real ROM bytes and asked to disassemble them, so the *opcodes* in
  its listing are consistent with the real ROM — but the labels, comments,
  and claims about *why* a bit does what it does are the model's inference,
  not verified against real hardware. It explicitly hedges some of this
  itself ("prawdopodobnie", "musisz to przetestować").

**Two concrete corrections found by cross-checking the chat against the real
schematic** (do not trust the chat on these points):

1. **8255 Port B is `$BF`, not `$5F`.** The schematic's own port-map note
   (top right of `U10`) reads: `PA $9F`, `PB $BF`, `PC $DF`, `CONF $FF`. Every
   message in the Arena chat says Port B is `$5F` — wrong, probably a
   plausible-sounding guess the model never corrected itself on.
2. **The front-panel button (`SW1`) pulls the Spectrum's `RST` line, not
   `/NMI`.** The schematic shows `SW1` (`SW_Push`) wired to a trace labelled
   `RST`, which is also one of the labelled `P1` edge-connector pins (the
   Spectrum's real `/RESET` line) — there is no `/NMI` signal anywhere in
   this schematic. The chat repeatedly asserts "Naciśnięcie przycisku
   generuje /NMI" and builds the whole bootstrap story around an NMI vector;
   that part needs to be rethought (most likely: the ROM is entered via a
   normal full reset, and the ROMCS decode logic — or the ROM's own code at
   whatever address the Spectrum's ROM vectors to post-reset — is what gets
   control, not an NMI handler). **Not yet re-derived from the gate network
   in the schematic** — flagged here as a known-wrong claim to fix before
   writing any NMI-handling code, not yet replaced with a verified answer.

Everything else from the chat (IEC bit-banging approach via 8255 Port C,
overall memory map, general component list, the TCP-bridge architecture
proposal) is plausible and matches the schematic's visible structure, but
still unverified in detail — treat procedure names/addresses in the
disassembly as a first-pass hypothesis, not fact, until cross-checked against
assembling the `.asm` back to the exact `SDI103J_ED3DC6CD.ROM` bytes.

## Hardware summary (from the real schematic)

**Memory map:**
- ROM: 4KB (`U8`, a 2764 EPROM) at `$3000–$3FFF`. `CE` (chip enable) is
  generated by the address-decode gate network (`U2A/U2B`, `U3A`,
  `U4A–U4D`, `U5A/U5B`, `U6A–U6D` — a mix of 74LS20/27/30/260/02) from
  `A15/A14/A13/A12/A11/A10`, `M1`, `MREQ`, `IORQ`. `ROMCS` also lights `D1`
  (LED) through `Q1` (BC547) and `U1E` (74LS06).

**I/O (8255 PPI, `U10`), per the schematic's own port-map label:**
| Port | Address | Pins |
|---|---|---|
| PA | `$9F` | PA0–PA7 |
| PB | `$BF` | PB0–PB7 |
| PC | `$DF` | PC0–PC7 |
| Control/CONF | `$FF` | — |

The `CS`/`RD`/`WR` of the 8255 and the PPI decode come from the same gate
network as `ROMCS` (`CE` signal), gated with `IORQ`.

**IEC bus:**
- `PC0` → `U1A` (74LS06, open-collector) → `ATN` (pull-ups `R5`/`R6`, 1kΩ, to
  VCC)
- `PC1` (`PC1` net also routed back to the EPROM's `CE`/program-enable side —
  worth re-checking exactly what `PC1` does both for IEC and for ROM control)
- → `U1B` → `CLK` (pull-ups `R8`/`R9`)
- → `U1C` → `DAT`
- `U1F` (74LS06) is explicitly marked `spare` — unused gate.
- `J1`, a DIN-6 connector labelled "IEC PORT / 1541 Disk Drive", with pins
  per the schematic: `2`→ATN, `4`→CLK, `5`→DAT, `3`→RES, plus GND. (Cross-
  check against a real Commodore serial-bus pinout reference before wiring
  anything physical — DIN-6 pin numbering conventions vary by source.)

**Power:** `U9` (LM7805, TO-220) regulates Spectrum's +9V edge-connector rail
down to +5V, with the usual decoupling caps (`C1–C7`).

**Reset:** `SW1` (push button) pulls the `RST` line (see correction #2 above
— this is the Spectrum's real `/RESET`, not an NMI).

**Edge connector (`P1`, `SPECTRUM_EDGE-28x2`):** full Z80 bus exposed —
`A0–A15`, `D0–D7`, `M1`, `MREQ`, `IORQ`, `RD`, `WR`, `RST`, plus `+9V`/`GND`.
Nothing exotic; same bus JASE already exposes to its other `Peripheral`s
(DivIDE, Multiface, ZiFi).

## Proposed software architecture (from the chat, matches JASE's existing conventions)

The chat's proposal lines up with how JASE already does things (`Peripheral`
base class, `ZiFi`'s own TCP-bridge-to-a-companion-process pattern — see
`src/ZiFi.h`/`src/ZiFi.cpp` and `tools/virtual_esp01/`): don't bit-bang IEC
timing inside JASE itself, bridge it over TCP to a separate process (Python
or C++) that either emulates a 1541 in software or drives a real Arduino +
physical IEC bus. The existing open-source project `c64-fdemu` already does
exactly the Arduino-bridge half of this (`C64 → IEC → Arduino → USB-serial →
PC → Python 1541 emulation`) and conveniently has a Python-side 1541
emulator already — reusable almost as-is for the PC end of this bridge, with
JASE's `SDI_Periphery` talking the same wire protocol `virtual_esp01`-style.

Sketch (from the chat, needs adapting to JASE's real `Peripheral` interface,
not the placeholder names below):

```cpp
class IECInterface {
public:
    virtual ~IECInterface() = default;
    virtual void setATN(bool state) = 0;
    virtual void setCLK(bool state) = 0;
    virtual void setDATA(bool state) = 0;
    virtual bool getDATA() = 0;
    virtual bool getCLK() = 0;
    virtual void delayMicroseconds(uint32_t us) = 0;
    virtual void onLineChange() = 0; // bridge reports a line change
};

class TCPBridgeClient : public IECInterface { /* ... */ };

class SDI_Periphery : public Peripheral {
    std::unique_ptr<IECInterface> iec;
    uint8_t portC_latch = 0xFF;
    const uint8_t* rom = nullptr; // SDI103J_ED3DC6CD_ROM
    bool rom_enabled = true;
    // in()/out() decode $9F/$BF/$DF/$FF (8255) same as ZiFi decodes its own ports
    // mem read for $3000-$3FFF when rom_enabled
};
```

Proposed wire protocol for the bridge (1 command byte + 1 data byte):
- `0x01 xx` — SET_LINES (`xx`: b0=DATA, b1=CLK, b2=ATN)
- `0x02` — GET_LINES (bridge replies with current line state)
- `0x03 nn` — DELAY_US (bridge can simulate real IEC timing)
- `0x04` — RESET

## Implementation status

**Done** — `src/SDI.h`/`src/SDI.cpp`, a `Peripheral` subclass, same shape as
`DivIde`/`Multiface`. `--sdi` / `--sdi-rom PATH` on the command line (off by
default, same convention as `--divide`/`--multiface1`).

- 8255 port decode: `(port & 0xFF & 0x9F) == 0x9F` selects the chip,
  `(port >> 5) & 3` picks PA(0)/PB(1)/PC(2)/CTRL(3) — derived with high
  confidence from the schematic's own published addresses sharing that bit
  pattern (not guessed), verified live via the debug protocol (`OUT`/`PORT`
  on `$9F`/`$BF`/`$DF`/`$FF` all round-trip correctly and independently; an
  unrelated port like `$1F` is correctly left unclaimed).
- ROM paging: constructed an 8K `MemoryMap::Bank` where the lower 4K
  ($2000–$2FFF) is snapshotted from whatever's *already* mapped at page 1
  (always the other half of a read-only ROM pair on every machine type —
  see `setupInitialPaging()` — so copying it once is safe, no write ever
  needs to land there instead) and the upper 4K ($3000–$3FFF) is the real
  SDI ROM. Page-in trigger is the **same first-pass hypothesis** flagged
  above as unverified in detail (M1 opcode fetch landing in $3000–$3FFF
  while not already active, DivIde/Multiface-style — not the chat's wrong
  NMI story), but it's no longer *just* a hypothesis: see the verification
  below.
- **Verified against the real ROM, not just built**: forced PC into
  `$3000` via the debug protocol's `--pc`/`--poke` test harness (same
  mechanism `main.cpp` documents for exercising a peripheral with no
  keyboard/window-manager path). The real ROM's own
  `L3000_PORT_DF_CLEAR_BIT2` routine (`IN A,($DF)` / `AND $FB` / `OUT
  ($DF),A` / a short delay loop / `RET`) then ran for real: `SDI`'s
  internal `portC_` latch changed from its `0xFF` default to exactly
  `0xFB` — bit 2 cleared, precisely matching `AND $FB`. That's direct
  evidence the ROM paged in correctly, executed real SDI code (not
  garbage) against the emulated 8255, and then `RET`-ed itself back out of
  the $3000–$3FFF window, at which point `onInstructionFetch()` correctly
  paged it back out again (confirmed `active=0` and the original page-1
  content restored afterward) — the full in→run→out cycle working
  end-to-end on the first real ROM it was tried against.

**ROMCS trigger boundary — narrowed from $3000-$3FFF to $3C00-$3FFF,
confirmed by four independent lines of evidence** (not just the
earlier single-test hypothesis above):

1. The schematic's own ROMCS gate-network inputs list exactly 6
   address lines (`A10-A15`), which decode a 1024-byte granularity —
   i.e. $3C00-$3FFF, not the full 4K.
2. The real ROM's own bytes have a 527-byte `0xFF` filler run from
   $39F1-$3BFF immediately *before* the first real code at $3C00 (five
   harmless `DI` opcodes as address-decode-slop margin, then real code
   starting at $3C05). $3000-$39F0 is real code too (confirmed by
   `BUGS.txt`'s own byte-offset patches landing in there), but it's
   only ever reached via internal `CALL`s from the $3C00+ entry code —
   never a direct M1 landing.
3. The ROM's own official README (`SDIv103J.TXT`) says verbatim:
   "Intercepts 128 ROM at $3C04 and performs a USR 0." A fresh
   disassembly (via the `z80dis` Python package, cross-checked byte-
   for-byte against the real ROM file, not the Arena chat's listing —
   see below) of $3C00-$3C11 matches exactly: `DI`×5 (padding) / `XOR
   A` / `OUT ($1FFD),A` / `LD B,$7F` / `LD A,$10` / `OUT ($7FFD),A` /
   `RST 0` — i.e. force 48K-compatible ROM/RAM paging, then restart.
   $3C18 onward (reached on a *separate* later M1 fetch, not a
   fall-through from `RST 0`) patches the stack slot pointed to by
   `ERR_SP` ($5C3D) to $3C5F, so a future BASIC syntax error (e.g.
   typing an unrecognized `*COMMAND`) redirects into SDI's own code
   instead of the normal "Nonsense in BASIC" — the real mechanism
   behind `*COMMAND`/`*CAT`, no NMI or separate hardware hook needed.
4. **Empirically confirmed** by booting JASE's own real, unmodified
   128K ROM (`/usr/share/fusex/128-0.rom`/`128-1.rom`, no SDI loaded at
   all) with a debug-protocol breakpoint at `$3C04` and a real
   `RESET`: it hits immediately and repeatedly, because $3C04 is part
   of the stock 128K menu's own keyboard-scan wait loop (`LD
   BC,$BFFE`/`IN A,(C)`/`BIT 0,A`/`JR Z,..`) — continuously executed
   from power-on, before a user ever sees the 128K menu. With SDI
   loaded, the *same* boot (now intercepted) shows `7FFD` forced to
   $10-then-$17 (48K ROM1 selected) within milliseconds, `active`
   correctly dropping back to 0 once PC leaves $3000-$3FFF, and a
   stable, non-crashed PC afterward — the narrowed trigger works
   end-to-end against the real ROM, not just in isolation.

**Cross-checking the Arena AI chat's own disassembly against the real
ROM bytes — a concrete example of why it's flagged as unverified.**
The chat independently guessed $3C5F was significant (calling it
`L3C5F_BOOTSTRAP_INIT`), which turned out to be directionally right —
but its *specific* claim, a standalone routine at $3C5F that prints
the DOS banner and installs hooks, does not match the real bytes. The
real banner text ("SPECTRUM DISK INTERFACE"/"DOS V1.03J") was
confirmed, byte-for-byte, to live at $32B1 (`rom.find(b"SPECTRUM DISK
INTERFACE")` against the real ROM file), and the real banner-print
loop is at $3C46-$3C50 — called from the $3C00 entry's own
continuation, not from a separate $3C5F routine. $3C5F in the real ROM
is used purely as a 16-bit *data value* (the vector written into the
`ERR_SP`-pointed stack slot), never a label the chat's imagined code
actually reaches. An earlier pass of the same chat also mislabeled the
port-$DF bit-twiddling routines by one slot (claiming $3006 is
`PORT_DF_SET_BIT2` when the real bytes show $300D is, with $3006-$300C
actually being a shared delay+`RET` tail the chat didn't account for).
Net: useful as a source of *hypotheses* about structure and purpose,
unreliable on specific addresses/labels — verify every claim against
the real ROM bytes with a disassembler before relying on it, same
discipline as the two corrections already documented above.

**PC0-7 bit mapping — confirmed, not guessed.** The rendered schematic PNG
wasn't legible enough on its own (wires cross too much at that resolution);
resolved by asking Pawel to check the actual KiCad schematic directly:

| Bit | Mask | Role |
|---|---|---|
| PC0 | 0x01 | ATN output (via U1A) — always driven by us, we're the controller |
| PC1 | 0x02 | separate, non-IEC signal (not understood yet, unused here) |
| PC2 | 0x04 | CLK output (via U1B) |
| PC3 | 0x08 | DAT output (via U1C) |
| PC4,PC5 | 0x10,0x20 | unused for IEC |
| PC6 | 0x40 | CLK read-back (tied to U1B's own output net, pulled up 1K) |
| PC7 | 0x80 | DAT read-back (tied to U1C's own output net) |

This 0-3-output/4-7-input split is exactly what 8255 mode 0 allows (each
nibble of Port C independently directioned) — a good independent sanity
check that the mapping is right, not a coincidence.

**IEC protocol facts — verified against a primary source, not memory.**
Before writing any bit-level timing logic, fetched and read the actual
ASCII timing diagrams from Commodore's own IEC Serial Bus Manual
(commodore.ca's reproduction — [raw text](https://www.commodore.ca/wp-content/uploads/2018/11/Commodore-IEC-Serial-Bus-Manual-C64-Plus4.txt)),
cross-checked against [pagetable.com's independent writeup](https://www.pagetable.com/201).
Both agree:
- All lines active-low (pulled low = logical 1/asserted).
- CLK is always generated by the active TALKER; **the RISING edge of CLK
  is when the DATA bit is valid** and gets sampled — this is the one
  load-bearing fact the whole byte-clocker below is built on.
- ATN: controller pulls it low: all devices must respond (pull DATA low)
  within 1000µs or it's a "device not present" error.
- End of a byte: listener pulls DATA low within 1000µs to acknowledge.
- EOI (last byte): sender delays starting the next bit by ≥200µs instead
  of the normal handshake timing; listener acks by holding DATA low
  ≥60-80µs then releasing.

**IEC byte-level decode — implemented and verified.** `SDI::clockBit()`
is a generic rising-edge-of-CLK shifter used in two phases:
- **Under ATN**: we're always the sender (we're the controller), clocked
  off our own driven CLK (PC2). Verified by hand-driving the exact real
  bit sequence for `LISTEN device 8` (`0x28`) through the debug protocol's
  `OUT DF ..` — `SDI`'s `lastByte_` came back as exactly `0x28`.
- **Post-ATN data phase**: direction depends on which PRIMARY address
  (not a secondary/channel byte) was last clocked under ATN — LISTEN
  (`0x20-0x3E`) means we keep sending (`IecRole::WeAreTalker`); TALK
  (`0x40-0x5E`) means the device sends and we receive
  (`IecRole::WeAreListener`); UNLISTEN/UNTALK (`0x3F`/`0x5F`) clear the
  role. Verified: after clocking LISTEN `0x28` under ATN, releasing ATN,
  then clocking a data byte with ATN low, `role` correctly stayed
  `weTalk` and the byte decoded correctly (LSB-first reconstruction
  confirmed bit-for-bit against what was actually sent).
- The `WeAreListener` direction is plumbed into `in()` (clocks off
  read-back CLK-in/PC6 instead of our own driven CLK) but can't produce
  real events yet — `clkLine()`/`datLine()` only ever reflect our OWN
  drive right now (no external device or bridge connected), so there's
  nothing to clock off until the TCP bridge exists.

**EOI and channel semantics — implemented and verified.**
- **EOI**: approximated via elapsed `onInstructionFetch()` calls (fires
  every Z80 instruction regardless of which peripheral is paged in) since
  the last bit clocked, rather than real microseconds — the real
  threshold is ≥200µs (~700 T-states @ 3.5MHz); `kIdleInstructionsForEoi`
  (40) is a rough per-instruction stand-in, explicitly flagged as an
  approximation in the code, not a verified exact count. Verified with
  the CPU stopped and `STEP` driving `onInstructionFetch()` deterministically
  (debug-protocol `OUT` alone doesn't execute instructions, so testing
  this needed real single-stepping, unlike everything else so far):
  clocking a byte with zero steps in between came back `eoi=0`; clocking
  one after 45 explicit `STEP`s came back `eoi=1`.
- **Channel/file semantics**: a secondary address under ATN is now
  decoded as OPEN (`0x60-0x6F`), CLOSE (`0xE0-0xEF`), or the plain
  channel-select KERNAL LOAD/SAVE convention (`0xF0-0xFF`) uses without a
  separate OPEN — standard, long-published CBM serial-bus facts, not
  specific to any one codebase. Data-phase bytes after an OPEN accumulate
  as a filename, committed to `filenames_[channel]` the moment
  UNLISTEN/UNTALK ends the exchange; after a plain-select, they're left
  as the just-finished LOAD/SAVE payload for inspection (`SDI FILES`)
  until the next secondary byte starts a new session. Verified
  end-to-end via the debug protocol: `LISTEN 8` → `OPEN channel 2`
  (`0x62`) → release ATN → clock `"TEST"` byte-by-byte → `SDI FILES`
  showed `bufLen=4 buf=TEST` mid-transfer → `UNLISTEN` → `SDI FILES`
  then showed `filenames=2:TEST,`, confirming the full OPEN→filename→
  commit path works.

**TCP bridge — implemented and verified end-to-end against a real test
disk.** `SDI::connectBridge()` (`--sdi-bridge HOST:PORT`) is a plain
blocking socket to `tools/c64iec_fs/c64iec_fs_tcp.py` — blocking, not
ZiFi's non-blocking `pump()`, matching the real Arduino-side
`IECSerialFile`'s own blocking-read design (see the licensing section
below for why reading that for its wire format is fine but copying it
isn't). OPEN/CLOSE/SAVE fire straight from `finalizeSession()` since the
whole payload is already decoded by then; LOAD's `R,<ch>,<size>` request
fires earlier, from `onSecondaryByte()` (while still under ATN), since
the bytes need to be ready before the Z80 starts polling for them —
landing in `pendingLoadData_`/`pendingLoadEoi_`, inspectable via `SDI
BRIDGE`.

**LOAD encoder — implemented and verified end-to-end against the real
bridge+disk.** `advanceLoadEncoder()` is the inverse of `clockBit()`: a
state machine (`Idle` → `WaitDataReady` → `BitSetup` → `BitValid` →
`WaitAck` → next bit/byte) that drives `deviceClk_`/`deviceDat_`
(exposed through `in()`'s PC6/PC7 synthesis when `role==WeAreListener`)
one half-step per `in()` poll, mirroring the Z80's own ready/ack
handshake on its side of the shared DATA line. Chunk refills
(`fetchMoreLoadData()`) fire transparently mid-stream when
`pendingLoadData_` runs out and `pendingLoadEoi_` isn't set yet.

Two real bugs were found and fixed while building and testing this
(both predate the encoder — it just was the first thing to actually
exercise the paths they live in):

- **PC6/PC7 read-back polarity.** PC6/PC7 are wired *directly* to the
  bus node (no inverting buffer, unlike PC0/2/3's output path through
  U1A/B/C) — the old code exposed them with the same polarity as the
  output bits, backwards for these two. Fixed in `in()`'s port-C case.
- **`clockBit()`'s CLK edge direction was backwards**, in every call
  site. The verified protocol fact is "CLK asserted → released is the
  sample point" (a 0→1 electrical transition given this project's
  "bit set = asserted" convention through the inverters); the original
  trigger fired on the opposite transition. This had passed every
  earlier single-byte test (`LISTEN 0x28`, `OPEN`+filename `TEST`)
  only because those hand-written test scripts held DATA constant
  across both halves of each bit, which reads the same value on either
  edge direction and completely masks the bug. It only surfaced once
  the LOAD encoder's `BitSetup`/`BitValid` states (which vary DATA
  correctly across the two phases, matching real hardware) exposed the
  mismatch. Fixed in both `out()`'s two `clockBit()` calls and the
  self-decode call in `in()`.

A third, structural issue surfaced only once multi-byte LOAD sequences
were actually driven through the encoder: the real IEC protocol
(re-verified against both primary sources — the Commodore manual's own
ASCII timing diagram and pagetable.com's independent step-by-step
writeup) inserts an **extra CLK release between every two bytes**
("talker ready to send"), electrically identical to a real per-bit
sample release and impossible to distinguish by edge direction alone.
The fix: the self-decode path in `in()` now decides off the encoder's
own state (`stateBefore == BitValid`) rather than a raw CLK edge, since
the state machine authoritatively knows which release is which. This
also fixed a related stale-exposure bug at the last bit of each byte
(`BitValid → WaitAck`), where the old post-call state check exposed
`datLine()` instead of the just-sampled bit — a real-hardware-visible
bug, not just a self-decode artifact, since it's the same bits a real
Z80 would be polling.

Verified against the real `AceofAces_SDI.d64` (not a synthetic file),
driven through the full `LISTEN`→`OPEN channel 0`→filename `*`→
`UNLISTEN`→`TALK`→plain-select→release-ATN sequence via the debug
protocol, acting as the "virtual Z80 listener" (releasing/asserting its
own DATA bit at the right points in each `WaitDataReady`/`WaitAck`
window): 260 bytes driven through the encoder, decoded via the
self-decode path into `SDI`'s own `dataBuf_`, matched byte-for-byte
against the bridge's own `pendingLoadData_` content at each chunk fetch
— including the exact 254-byte chunk-refetch boundary, where a byte
count or state-machine desync would have shown up immediately.
(Confirming this needed the debug protocol's `SDI`/`SDI BRIDGE` reply
buffers bumped from 340-400 chars to 1536 — the originals silently
truncated a full 254-byte chunk's hex-escaped preview well before the
boundary, which first looked like a decode mismatch and wasn't.)

Still deliberately not implemented: talker-side EOI signaling for a
LOAD's actual last byte (the encoder currently treats it like any
other byte, per the EOI approximation discussion above — the consumer
side, i.e. byte-level decode of an incoming EOI flag, already works;
only the encoder's own "delay before the final byte" signal is
missing).

**SAVE-direction listener ack — implemented and verified.** The
`WeAreTalker` direction (OPEN filenames, SAVE payload) used to only
self-decode the Z80's own CLK/DATA writes without ever driving a
"virtual listener" ack back onto the DATA line, unlike the LOAD
encoder's `WaitAck` state in reverse — meaning a real Z80 ROM that
actually waits for the addressed device to acknowledge each byte
(per the same primary-source protocol used above) would have stalled
against this emulation. Fixed by giving `SDI` a `listenerDat_` bit
(exposed through `in()`'s PC7 synthesis whenever `role==WeAreTalker`,
the mirror image of the LOAD path's `deviceDat_`) that plays the
addressed device's own listener role: released ("ready for data")
once the sender's inter-byte "ready to send" CLK release arrives,
asserted ("byte accepted") the instant `clockBit()` completes a byte —
the exact reverse of `advanceLoadEncoder()`'s own
`WaitDataReady`/`WaitAck` handshake.

This also resolved the matching receive-side half of the "extra
ready-to-send CLK release between bytes" ambiguity (see the LOAD
encoder section above): `clockBit()` itself now tracks a shared
`awaitingInterByteRelease_` flag, set the instant a byte completes (or
a fresh ATN/data-phase session starts, alongside its existing
`bitCount_`/`shiftByte_` reset in `out()`) and consumed — without
counting as a bit — the next time a CLK edge arrives. Since both of
`out()`'s `clockBit()` call sites (ATN-phase command bytes and
WeAreTalker data-phase bytes) now share this one flag, both benefit
from the fix, not just the WeAreTalker path the ack driver itself
targets.

Verified end-to-end via the debug protocol, acting as a protocol-
faithful sender that honours the new ack handshake (releasing CLK for
"ready to send", waiting for `listenerDat_` to release before clocking
8 bits, then waiting for it to re-assert before the next byte): a
`LISTEN 8` → `OPEN channel 3` → 8-character filename (`DISKFILE`,
crossing 8 byte boundaries) → `UNLISTEN` sequence came back with
`filenames=3:DISKFILE` — exact, byte-for-byte, with every single
ack wait resolving instead of timing out. A second run, `LISTEN 8` →
plain-select channel 5 → a 16-byte payload (crossing 16 byte
boundaries, including non-printable bytes `0x00/0xFF/0x7F/0xAA/...` to
exercise the hex-escaped debug readout) → `UNLISTEN`, came back with
`buf=\x00\x01\x02\xff\x7fABCDE\xaaU\x00\xfe\x10\x99` — again exact.
Both runs would have produced garbage from the second byte onward had
either the ack handshake or the byte-boundary fix been wrong, since a
real sender only proceeds past the inter-byte release once it observes
the listener's ack. Talker-side EOI signalling for an actual SAVE's
last byte (the ATN-phase/WeAreTalker byte stream has no notion of
"this is the final byte" yet, mirroring the LOAD encoder's own
still-missing talker-side EOI noted above) remains unbuilt.

Verified against the REAL disk images under `docs/VC1541/web/.../disk/`
(`AceofAces_SDI.d64`), not a synthetic test file: forced the exact IEC

## USR 16000 activation, and the "boot banner" correction

**`$3E80` (decimal 16000) confirmed as the real, documented activation
entry point — matches a NEW primary source, not disassembly guessing.**
`SDI_Command.pdf` (the hardware/firmware authors' own magazine article,
"Moj Mikro" 1986 №07, pages 32-33+23 — a far more authoritative source
than the Arena AI chat) says verbatim: *"What you need to remember is
to type RANDOMIZE USR 16000 before starting to work with SDI, preferably
immediately after turning on the computer. The same instruction must
also be the first in the program that uses SDI commands... Apart from
the connection to SDI, the command also executes `BORDER 1: PAPER 1:
INK 7: CLS` on first execution."* $3E80 = 16000 decimal exactly, and
it's the known internal `JP $3C18` target found earlier (see the
ROMCS boundary section above) — independently confirmed correct from
two completely different angles now.

**Verified live**, bypassing the real Sinclair BASIC keyword-entry
system entirely (see "why not just TYPE it" below): stopped the CPU at
the idle loop's own `RET` (`$1600`), overwrote the return address on
the stack with `$3E80` via the debug protocol's `POKE`/`MEM`, then
`STEP`-ped — landed exactly on `$3E80`, which (correctly, since $3E80
falls in the $3C00-$3FFF ROMCS window) paged SDI in and ran `JP
$3C18` → `active=1`. Continuing: it called out to the stock ROM's own
CHAN-OPEN (`$1601`) and a ROM-internal routine around `$0E5C`/`$0D6B`
(pageOut correctly fired while in stock-ROM territory, pageIn fired
again on return — the paging mechanism handles this "call out, call
back in" pattern correctly), then a 100-iteration loop through `$3E2B`
(`PUSH AF`/`EI`/`RST 16`/`DI`/`POP AF`/`RET` — the real, standard
Spectrum "print one character to the current channel" wrapper).

**Correction: there is no "DOS banner" that prints automatically.**
The Arena AI chat's `L3C5F_BOOTSTRAP_INIT` claim ("prints the DOS
banner, installs hooks") was already flagged as unreliable on specifics
(the real banner text lives at $32B1, not called from $3C5F — see the
ROMCS section above). It turns out the chat's underlying PREMISE — that
*any* banner gets printed on activation — was also wrong, not just
mis-placed. `SDI_Command.pdf` is explicit and primary-source: the ONLY
visible effect of `RANDOMIZE USR 16000` is `BORDER 1: PAPER 1: INK 7:
CLS`, no text. The 100-byte loop at $32AD (which earlier looked like a
banner-print loop purely because $32B1 — 4 bytes into that same range —
happens to hold the readable "SPECTRUM DISK INTERFACE" string
elsewhere referenced in the ROM) is something else — plausibly 1541
IEC reset/init bytes being pushed through the character-output
mechanism as a convenient byte-sink via a newly-installed custom
channel (`LDIR`-copied from `$3313` to the address `$5C7B` points at,
then `CURCHL` ($5C51) retargeted to it) — not human-readable text.
Live-tested screen state after the full call chain completed: bitmap
all zero (consistent with `CLS` having run), but `ATTR_P` ($5C8D) read
back `0x84` (paper=black/ink=green/flash), not the documented
paper=1/ink=7 — the stack-hijack entry point likely isn't 100%
equivalent to a genuine `RANDOMIZE USR 16000` BASIC call (e.g. a
register the real USR-call convention sets that this shortcut didn't),
so border/paper/ink wasn't confirmed pixel-for-pixel yet. Flagged here
as the next thing to pin down, not quietly accepted.

**Why not just `TYPE "RANDOMIZE USR 16000"` through the keyboard
sim?** Tried first, and it's a real methodology gap worth recording:
JASE's debug-protocol `TYPE` command spells text out via individual
PC-keyboard-style letter keypresses. On a real Spectrum, BASIC
keywords are NOT entered by spelling them out — in "K" (keyword)
cursor mode, a single unshifted letter keypress (e.g. "R") produces an
entire reserved word (its own meaning depends on cursor mode), not the
literal letter. Spelling "R-A-N-D-O-M-I-Z-E" through `TYPE` typed the
keyword for the first letter, then kept going in whatever mode followed,
literally spelling "andomize" as if it were a variable name — confirmed
by the exact error produced: `2 Variable not found, 0:1`. A second
pitfall found along the way: `PRESSKEYS`/`TYPE` both call
`MinZX::pressKeys()`, which unconditionally clears the whole queued-key
buffer (`autoTypeSeq_.clear()`) — calling `TYPE` then a separate
`PRESSKEYS RETURN` wipes out the just-typed text before any of it is
delivered, so RETURN arrives alone on an empty line. Properly testing
through the keyboard requires either keyword-aware single-keystroke
entry (matching the real K/L/C/E cursor-mode system `*CAT`'s own
"extended mode + 9" entry already hints at) or driving it the way this
session did — directly via the debug protocol, bypassing the keyboard
simulation's current ASCII-letter-spelling limitation.

## Bridging to a real/virtual 1541 — `c64-fdemu`

Pawel's plan: reuse `fox20io/c64-fdemu` (https://github.com/fox20io/c64-fdemu)
— specifically its `src/fileserver/c64iec_fs.py`, which already does real
file-serving (wildcard resolution, directory listing, chunked reads with
progress reporting — seen working live against a real C64 in a screenshot)
— by swapping its current USB-serial-to-an-Arduino transport for a plain TCP
socket, "resztę architektury zostawiam tobie" (architecture otherwise left
to me), with the one constraint that JASE's side follows the existing
`Peripheral` convention.

**Licensing: both `c64-fdemu` and the `IECDevice` library it bundles
(`src/iec2usb/lib/IECDevice-main/`) are GPLv3** (confirmed by reading their
`LICENSE` files directly). Per this project's established practice all
session (`ZiFi`, `tools/virtual_esp01`, the `Gopher`/`Tnfs` clients were all
written clean-room specifically to keep GPL code out of JASE's own,
MIT-licensed tree) — **no code from either gets copied into JASE.** What
*is* fair game, and what the rest of this section is built from: reading
`IECSerialFile.cpp`/`.h` (the Arduino-side class whose job is exactly
"forward file ops to a host computer over serial", the thing being replaced
with "forward over TCP") purely for the **wire protocol it already uses** —
a fact about an interoperability format, not a copyrightable expression,
same category as the pico-spec/fusex port-number facts already reused
elsewhere in this project. Pawel's own copy of `c64iec_fs.py`, patched to
listen on TCP, can be run entirely outside the JASE repo as his own separate
GPL tool — nothing about that requires vendoring GPL code into JASE at all.

**The real wire protocol** (read directly from `IECSerialFile.cpp`, not
guessed — `CHUNK_SIZE` is 128, from `IECSerialAdapterConfig.h`):

| Direction | Format | Meaning |
|---|---|---|
| → host | `O,<ch_hex>,<name>\n` | open `name` on channel `ch` |
| ← host | `OK...\n` or anything else | open succeeded / failed |
| → host | `R,<ch_hex>,<chunksize>\n` | request up to `chunksize` bytes |
| ← host | `<M\|L\|E>,<n>\n` + `n` raw bytes | `M`=more follows, `L`=last chunk (EOI), `E`=error/EOF (no bytes follow) |
| → host | `W,<ch_hex>,<n>,<E\|C>\n` + `n` raw bytes | write `n` bytes, `E`=this is the last write (EOI), `C`=more follow |
| ← host | `OK...\n` or anything else | write accepted / rejected |
| → host | `C,<ch_hex>\n` | close channel `ch` |
| ← host | (one line, ignored) | ack |

**What JASE's side actually has to do, in three layers** (clarifying the
"architecture" the chat sketched, now that the real library's shape is
known): `IECSerialFile`/`IECFileDevice` on the Arduino do NOT implement raw
electrical IEC bit-banging themselves — that's `IECBusHandler`/`IECDevice`,
a layer below, driving real pins with microsecond timing. JASE has no real
pins to drive and doesn't need that layer at all. What JASE's `SDI`
peripheral *does* need, because the real ROM bit-bangs IEC electrically
through the emulated 8255 Port C, is the **middle** layer — the genuinely
public, not-GPL-specific Commodore IEC bus protocol (ATN assertion,
TALK/LISTEN device addressing, OPEN/CLOSE/byte-level read-write handshake,
EOI) — decoded from Port C's bit transitions, clean-room, the same way
`ZiFi` decodes its own ZX-Uno bit-level register writes rather than copying
pico-spec's GPL code for it. Once that layer turns a 74LS06-level bit
sequence into a clean "channel N opened with name X" / "byte arrived on
channel N" event, the **outer** layer is just forwarding that event over
TCP using the wire format above — the part `IECSerialFile` already shows
the shape of, and the part Pawel's own patched `c64iec_fs.py` (external,
GPL, his) answers.

jak komunikują się z 8255, jak obsługują IEC (bit-banging przez 74LS06),

### 1. Maksymalne ulepszenie drop-in (bez zmiany PCB)

**IC (wszystkie footprinty identyczne):**

- Wszystkie układy logiczne 74LSxx (74LS30, 74LS20, 74LS02, 74LS27, 74LS260, 74LS520, 74LS245, 74LS06 itd.) → **74AHCTxx** (najlepsza kombinacja prędkości, poboru prądu i kompatybilności 5V).

Szczególnie ważne: **U11 (74LS06) → 74AHCT06** (zachowuje open-collector, lepsze czasy narastania na IEC).
- U8 (2764 EPROM) → **AT28C64B-15PU** (EEPROM, nie wymaga kasowania UV) lub **W27C64-45Z**.
- U10 (8255) → **82C55A-5** (CMOS, wyraźnie niższy pobór prądu).
- U9 (LM7805) → **RECOM R-785.0-1.0** lub **Murata OKI-78SR-5/1.5W** (switching drop-in, prawie zero ciepła, ten sam pinout TO-220/SIP).
- Tranzystory BC547 → **2N3904** lub **BC547C**.

**Pasywa i inne:**

- Wszystkie kondensatory 100nF → 100nF 50V X7R MLCC.
- C2 100µF → 220µF 25V 105°C low-ESR.
- Rezystory pull-up na liniach IEC (1kΩ) → **2.2kΩ 1%** (lepsza kompatybilność z prawdziwym 1541).
- Gniazda → machined pin gold-plated (wszystkie układy).
- LED → niskoprądowa 1–2 mA + dobrany rezystor.

Efekt: znacznie niższy pobór prądu, mniej ciepła, stabilniejsza 
praca IEC, brak potrzeby radiatora na 7805, łatwiejsze programowanie 
pamięci (EEPROM).


### 2. Pełny plik SDI103J.asm (~2000 linii z komentarzami)


```
asm; ================================================================
; SDI – ZX SPECTRUM 1541 Disk Interface
; DOS V1.03J
; Hardware: Uros Milan
; Software: Geren Ivan
; PCB: Mario Prato Rev 1.0 (sdi.kicad.sch)
; ROM: 4KB mapped at $3000-$3FFF
; I/O: 8255 at ports $9F (PA), $5F (PB), $DF (PC), $FF (CTRL)
; IEC via 74LS06 (U11) open-collector + 1k/2.2k pull-ups
; ================================================================

    org     $3000

; ================================================================
; PORT_DF MANIPULATION - L3000
; ================================================================
L3000_PORT_DF_CLEAR_BIT2:
    in      a,($df)         ; odczyt Port C 8255 (linie IEC status + control)
    and     $fb             ; wyczyść bit 2 (zazwyczaj jeden z bitów ATN/CLK/DATA)
    out     ($df),a         ; zapisz z powrotem
    ret

; ================================================================
; OPÓŹNIENIA (delay loops) - używane przy bit-banging IEC
; ================================================================
DELAY_1MS:
    push    bc
    ld      b, $c8          ; ~1ms przy 3.5MHz Spectrum
.loop:
    djnz    .loop
    pop     bc
    ret

DELAY_SHORT:
    nop
    nop
    ret

; ================================================================
; IEC_LOW_LEVEL - L3025 IEC_SEND_BYTE
; Wysyła bajt po IEC (standard Commodore serial bus)
; Wejście: A = bajt do wysłania
; ================================================================
L3025_IEC_SEND_BYTE:
    push    bc
    ld      b,8             ; 8 bitów
    ld      c,a             ; zachowaj bajt

.bit_loop:
    srl     c               ; bit do carry
    call    IEC_SET_DATA    ; ustaw linię DATA zgodnie z carry

    call    IEC_PULSE_CLK   ; zegar (CLK low->high)
    call    DELAY_SHORT

    djnz    .bit_loop

    call    IEC_RELEASE_DATA
    pop     bc
    ret

IEC_SET_DATA:
    in      a,($df)
    jr      c,.release
    and     $fe             ; DATA=0 (przez 74LS06)
    jr      .write
.release:
    or      $01             ; DATA=1 (pull-up)
.write:
    out     ($df),a
    ret

IEC_PULSE_CLK:
    in      a,($df)
    and     $fd             ; CLK=0
    out     ($df),a
    call    DELAY_SHORT
    or      $02             ; CLK=1
    out     ($df),a
    ret

IEC_RELEASE_DATA:
    in      a,($df)
    or      $01
    out     ($df),a
    ret

; ================================================================
; IEC_ATN_SEND_COMMAND
; Wysyła komendę z ATN active (typowe dla 1541)
; ================================================================
IEC_ATN_SEND:
    call    IEC_SET_ATN_LOW
    call    L3025_IEC_SEND_BYTE
    call    IEC_SET_ATN_HIGH
    ret

IEC_SET_ATN_LOW:
    in      a,($df)
    and     $f7             ; bit ATN
    out     ($df),a
    ret

IEC_SET_ATN_HIGH:
    in      a,($df)
    or      $08
    out     ($df),a
    ret

; ================================================================
; DOS_COMMAND_DISPATCH - $30A2
; Główny dispatcher komend BASIC (LOAD, SAVE, RUN, OPEN, CLOSE...)
; ================================================================
L30A2_DOS_COMMAND_DISPATCH:
    call    L3000_PORT_DF_CLEAR_BIT2
    call    READ_BASIC_COMMAND      ; parsuje komendę z BASIC
    jr      nz,.unknown

    ld      hl,COMMAND_TOKEN_TABLE
    call    MATCH_TOKEN             ; porównuje z tokenami w $31A9
    jp      z,HANDLE_COMMAND        ; $30D4

.unknown:
    ld      hl,MSG_SYNTAX_ERROR
    call    PRINT_MESSAGE
    xor     a
    ret

; ================================================================
; HANDLE_COMMAND - $30D4
; Rozgałęzienie według tokenu
; ================================================================
L30D4_HANDLE_COMMAND:
    push    hl
    ld      a,(COMMAND_TOKEN)
    cp      $01                     ; LOAD ?
    jr      z,CMD_LOAD
    cp      $02                     ; SAVE ?
    jr      z,CMD_SAVE
    cp      $03                     ; VERIFY
    jr      z,CMD_VERIFY
    cp      $10                     ; OPEN
    jr      z,CMD_OPEN
    ; ... kolejne komendy

    pop     hl
    ret

; ================================================================
; COMMAND_TOKEN_TABLE - $31A9
; ================================================================
COMMAND_TOKEN_TABLE:
    db      "LOAD",0,   $01
    db      "SAVE",0,   $02
    db      "VERIFY",0, $03
    db      "OPEN",0,   $10
    db      "CLOSE",0,  $11
    db      0

; ================================================================
; CMD_LOAD
; Wysyła "M-R" / "M-W" / "U1" do 1541, odbiera dane, przekazuje do Spectrum
; ================================================================
CMD_LOAD:
    ld      hl,MSG_SEARCHING_FOR
    call    PRINT_MESSAGE
    ld      hl,FILENAME_BUFFER
    call    IEC_SEND_FILENAME_WITH_ATN

    ld      a,$f0                   ; komenda LOAD w 1541
    call    IEC_ATN_SEND

    call    IEC_RECEIVE_BYTE
    cp      $00                     ; status OK?
    jr      nz,LOAD_ERROR

    ld      hl,MSG_LOADING
    call    PRINT_MESSAGE

    call    RECEIVE_AND_POKE_TO_MEMORY
    pop     hl
    scf                             ; success
    ret

LOAD_ERROR:
    ld      hl,MSG_FILE_NOT_FOUND
    call    PRINT_MESSAGE
    pop     hl
    ret

; ================================================================
; IEC_RECEIVE_BYTE
; Odbiór bajtu z IEC (bit-banging)
; ================================================================
IEC_RECEIVE_BYTE:
    push    bc
    ld      b,8
    ld      c,0
.loop:
    call    IEC_WAIT_CLK
    in      a,($df)
    rrca                            ; bit DATA
    rr      c
    djnz    .loop
    ld      a,c
    pop     bc
    ret

; ================================================================
; Tabela komunikatów (z oryginalnymi stringami)
; ================================================================
MSG_SEARCHING_FOR:
    db      $0d,"SEARCHING FOR ",$00
MSG_LOADING:
    db      "LOADING",$0d,$00
MSG_SAVING:
    db      "SAVING",$0d,$00
MSG_VERIFYING:
    db      "VERIFYING",$0d,$00
MSG_FILE_NOT_FOUND:
    db      $0d,"FILE NOT FOUND",$0d,$00
MSG_DEVICE_NOT_PRESENT:
    db      $0d,"DEVICE NOT PRESENT",$0d,$00
MSG_ERROR:
    db      $0d,"ERROR",$0d,$00
MSG_DOS_BANNER:
    db      $0d,$0d,"SPECTRUM DISK INTERFACE"
    db      $0d,"DOS V1.03J"
    db      $0d,"AUTORI HARDVERA: UROS MILAN"
    db      $0d,"SOFTVERA: GEREN IVAN",$0d,$8d

; ================================================================
; BOOTSTRAP_INIT - $3C5F (lub okolice $3F00)
; Inicjalizacja przy starcie Spectrum, patchuje wektory ROMu
; ================================================================
L3C5F_BOOTSTRAP_INIT:
    ld      hl,MSG_DOS_BANNER
    call    PRINT_MESSAGE

    ; Patch BASIC vectors / system variables
    ld      hl,NEW_COMMAND_HOOK
    ld      ($5c5b),hl              ; ERR-SP / hook komend

    ld      a,$cd                   ; CALL
    ld      ($5c92),a               ; patch PRINT/INPUT etc. jeśli potrzeba

    call    INIT_8255               ; konfiguracja 8255 (mode 0, output)
    ld      a,$80
    out     ($ff),a

    jp      $0000                   ; powrót do BASIC

INIT_8255:
    ld      a,$80                   ; wszystkie porty output
    out     ($ff),a
    ret

NEW_COMMAND_HOOK:
    call    L30A2_DOS_COMMAND_DISPATCH
    ret

; ================================================================
; PRINT_MESSAGE
; Używa standardowych procedur Spectrum ROM ($0a something)
; ================================================================
PRINT_MESSAGE:
    ld      a,(hl)
    or      a
    ret     z
    rst     $10                     ; PRINT
    inc     hl
    jr      PRINT_MESSAGE

; ================================================================
; Pozostałe procedury (skrócone dla czytelności - pełne ~2000 linii)
; ================================================================
; $31xx-$33xx : parser komend, token matching, filename handling
; $34xx-$37xx : IEC high-level (send program, load PRG, directory)
; $38xx-$3Bxx : error handling, status from 1541 (device 8/9)
; $3C00-$3FFF : bootstrap, vectors, data tables, copyright banner

; Pełna deasemblacja reszty obszaru (od $3100 do $3FFF) zawiera:
; - MATCH_TOKEN (porównuje string z COMMAND_TOKEN_TABLE)
; - SEND_M_W_COMMAND (M-W do 1541 - memory write)
; - READ_DISK_STATUS (odbiera "73,..." error channel)
; - DIRECTORY_LISTING (używane przy CAT)
; - SAVE routine (U2 / "S:" + filename)
; - liczne tabele lookup dla error codes 1541
; - delay loops dostrojone pod timing IEC 1541

    ; wypełniacz do 4KB (oryginalny ROM ma konkretne bajty)
    org     $4000
    end
```

### **CZĘŚĆ 1/4** – Nagłówek, Equates, Low-level IEC + Port DF ($3000–$31AF)


```
asm; ================================================================
; SDI – ZX SPECTRUM 1541 Disk Interface
; DOS V1.03J
; Hardware: Uros Milan
; Software: Geren Ivan
; ROM: 4KB @ $3000-$3FFF
; I/O: 8255 PPI
;   PA = $9F, PB = $5F, PC = $DF, Control = $FF
; IEC bus via 74LS06 (U11) open-collector + pull-ups
; ================================================================

    org     $3000

; ================================================================
; EQUATES
; ================================================================
PORT_PA         equ $9f
PORT_PB         equ $5f
PORT_PC         equ $df     ; najczęstszy port używany do IEC
PORT_CTRL       equ $ff

IEC_ATN         equ $08     ; bit 3
IEC_CLK         equ $02     ; bit 1
IEC_DATA        equ $01     ; bit 0
IEC_RESET       equ $10     ; bit 4 (rzadziej używany)

CMD_LOAD        equ $01
CMD_SAVE        equ $02
CMD_VERIFY      equ $03
CMD_OPEN        equ $10
CMD_CLOSE       equ $11

; ================================================================
; L3000 - PORT_DF_CLEAR_BIT2
; Najczęściej wywoływana procedura na początku komend
; Czyści bit 2 w porcie PC (używany do sygnalizacji gotowości)
; ================================================================
L3000_PORT_DF_CLEAR_BIT2:
    in      a,(PORT_PC)         ; odczyt aktualnego stanu linii IEC + control
    and     $fb                 ; maska ~00000100 - czyści bit 2
    out     (PORT_PC),a
    ret

; ================================================================
; Opóźnienia używane przy bit-banging IEC (dostroje pod 3.5MHz Spectrum)
; ================================================================
L300C_DELAY_1MS:
    push    bc
    ld      b,$c8               ; ~1ms
.loop:
    djnz    .loop
    pop     bc
    ret

L3014_DELAY_SHORT:
    nop
    nop
    nop
    ret

; ================================================================
; L3025_IEC_SEND_BYTE
; Wysyła 8 bitów po magistrali IEC (standard Commodore serial)
; Wejście: A = bajt do wysłania
; ================================================================
L3025_IEC_SEND_BYTE:
    push    bc
    ld      b,8
    ld      c,a                 ; bajt do wysłania
.bit_loop:
    srl     c                   ; najniższy bit -> Carry
    call    L3040_IEC_SET_DATA_FROM_CARRY
    call    L3058_IEC_PULSE_CLK
    call    L3014_DELAY_SHORT
    djnz    .bit_loop

    call    L3065_IEC_RELEASE_DATA
    pop     bc
    ret

; Ustawia linię DATA zgodnie z Carry
L3040_IEC_SET_DATA_FROM_CARRY:
    in      a,(PORT_PC)
    jr      c,.data_high
    and     ~IEC_DATA           ; DATA = 0 (aktywacja przez 74LS06)
    jr      .write
.data_high:
    or      IEC_DATA            ; DATA = 1 (pull-up)
.write:
    out     (PORT_PC),a
    ret

L3058_IEC_PULSE_CLK:
    in      a,(PORT_PC)
    and     ~IEC_CLK            ; CLK = 0
    out     (PORT_PC),a
    call    L3014_DELAY_SHORT
    or      IEC_CLK             ; CLK = 1
    out     (PORT_PC),a
    ret

L3065_IEC_RELEASE_DATA:
    in      a,(PORT_PC)
    or      IEC_DATA
    out     (PORT_PC),a
    ret

; ================================================================
; IEC ATN routines
; ================================================================
L3070_IEC_SET_ATN_LOW:
    in      a,(PORT_PC)
    and     ~IEC_ATN
    out     (PORT_PC),a
    ret

L3078_IEC_SET_ATN_HIGH:
    in      a,(PORT_PC)
    or      IEC_ATN
    out     (PORT_PC),a
    ret

L3080_IEC_ATN_SEND_COMMAND:
    call    L3070_IEC_SET_ATN_LOW
    call    L3025_IEC_SEND_BYTE
    call    L3078_IEC_SET_ATN_HIGH
    ret

; ================================================================
; Odbiór bajtu z IEC
; ================================================================
L3090_IEC_RECEIVE_BYTE:
    push    bc
    ld      b,8
    ld      c,0
.loop:
    call    L30B0_IEC_WAIT_CLK_HIGH
    in      a,(PORT_PC)
    rrca                        ; DATA na bit 0
    rr      c                   ; przesuwamy do C
    djnz    .loop
    ld      a,c
    pop     bc
    ret

L30B0_IEC_WAIT_CLK_HIGH:
    in      a,(PORT_PC)
    bit     1,a                 ; test bit CLK
    jr      z,L30B0_IEC_WAIT_CLK_HIGH
    ret

; ================================================================
; L30A2 - DOS_COMMAND_DISPATCH (główny punkt wejścia z BASIC)
; ================================================================
L30A2_DOS_COMMAND_DISPATCH:
    call    L3000_PORT_DF_CLEAR_BIT2
    call    L3100_READ_BASIC_COMMAND
    jr      nz,.syntax_error

    ld      hl,COMMAND_TOKEN_TABLE
    call    L3120_MATCH_TOKEN
    jp      z,L30D4_HANDLE_COMMAND

.syntax_error:
    ld      hl,MSG_SYNTAX_ERROR
    call    L3200_PRINT_MESSAGE
    xor     a
    ret
```

| Port | Typ | Opis |

| $FF | OUT | Rejestr sterujący 8255 (OUT ($FF), $80— tryb 0, wszystkie porty wyjściowe). |

- "SOFTVERA: GEREN IVAN"

- Obsługuje standardowe tokeny BASIC (LOAD, SAVE, VERIFY, OPEN, CLOSE itp.).
- Procedury:
- `L30D4_HANDLE_COMMAND`
- `CMD_LOAD_HANDLER`
- `L3200_PRINT_MESSAGE` (używa `RST $10`)
- `L3500_READ_DISK_STATUS`

Kluczowe procedury niskiego poziomu:

- `L3025_IEC_SEND_BYTE`
- `IEC_SET_DATA_FROM_CARRY`
- `IEC_PULSE_CLK`
- `IEC routines` używające portu `$DF`

Interfejs działa jako **IEC Master** (podobnie jak 
C64), komunikując się z napędem 1541 lub kompatybilnym. Linie DATA, CLK,

- **/NMI** – przycisk na płytce (główny sposób wejścia do DOS).

### **SDI (Spectrum Disk Interface) – Specyfikacja dla Peripheria / MinZX_SDL**


#### **1. Cel implementacji**

Emulacja
 kartridża SDI (UROS MILAN + GEREN IVAN, DOS V1.03J) jako drop-in 
urządzenie w tablicy peryferiów. Ma działać zarówno ze stockowym ROM-em (`SDI103J_ED3DC6CD_ROM`), jak i z nowym firmwarem pisanym przez użytkownika.


#### **2. Memory Map**

- **ROM**: 4096 bajtów, mapowany na zakres **`0x3000 – 0x3FFF`**
- Gdy ROM jest włączony → całkowicie zasłania RAM Spectrum w tym zakresie (read zwraca bajt z ROM-u).
- Zapis do `0x3000-0x3FFF` powinien być ignorowany (ROM nie jest zapisywalny).
- **Sterowanie ROM-em**:
- Port **`0xDF`**, bit 2
- `bit 2 == 0` → ROM włączony
- `bit 2 == 1` → ROM wyłączony (widoczny normalny RAM Spectrum)
- Procedura z ROM-u: `L3000_PORT_DF_CLEAR_BIT2` robi `AND $FB` na porcie `$DF`.


#### **3. I/O Ports (najważniejsze)**

| Port | Typ | Nazwa w disassembly | Opis |
|---|---|---|---|
| 0xDF | R/W | PORT_PC | Główny port– IEC + sterowanie ROM-em + latch |
| 0xFF | W | — | 8255 Control Register– zwykle pisane wartością0x80(Mode 0, wszystkie porty wyjściowe) |
| 0x9F | R/W | — | Dostęp do Port A lub B 8255 (partial decode) |
| 0x5F | R/W | — | Dostęp do Port A lub B 8255 (partial decode) |

**Szczegóły portu `0xDF` (PORT_PC)**:

- Bit 2 – ROM control (0 = enabled)
- Pozostałe bity używane do bit-bangingu IEC (DATA, CLK, ATN)
- Kod ROM-u wykonuje operacje:
- `in a,(0xdf)`
- `and $fb` / `or $04`
- `srl c` + operacje na carry (IEC_SET_DATA_FROM_CARRY)
- `out (0xdf),a`
- Kluczowe procedury do przeanalizowania: `L3025_IEC_SEND_BYTE`, `IEC_SET_DATA_FROM_CARRY`, `IEC_PULSE_CLK`, `IEC_WAIT_FOR_DATA_HIGH` itp.


#### **4. NMI / Bootstrap**

- Przycisk na kartridżu pociąga linię **/NMI** w dół.
- Wywołuje procedurę **`0x3C5F`** (`L3C5F_BOOTSTRAP_INIT`) znajdującą się w ROM-ie.
- Co robi bootstrap:
- Włącza ROM (czyści bit 2 w porcie `$DF`)
- Wyświetla baner (`SPECTRUM DISK INTERFACE`, `DOS V1.03J`)
- Instaluje własny hook komend BASIC-a pod adresem **`$5C5B`** (lub okolicznym – patrz `NEW_COMMAND_HOOK`)
- Inicjalizuje 8255 (`out (0xff), 0x80`)
- Ustawia stan IEC
- Wraca z NMI


#### **5. Sygnały CPU i magistrala**

- Pełne podłączenie do magistrali Z80:

- `/MREQ`, `/IORQ`, `/RD`, `/WR`, `/M1`
- `A0–A15`, `D0–D7`
- `/NMI`
- CLK (brak własnego generatora – używa zegara Spectrum)
- Adresowanie dekodowane przez układ 74LS (U2–U7). Nie trzeba emulować 
każdego 74LS-a – wystarczy poprawne zachowanie portów i mapowania 
pamięci.


#### **6. IEC (Commodore Serial Bus)**

- Całkowicie **bit-banged** przez port `$DF`.
- Nie używa dedykowanego chipu UART/6522 – cały protokół ATN/CLK/DATA 
jest realizowany w assemblerze Z80 z precyzyjnymi opóźnieniami.
- W emulatorze zalecane jest stworzenie **wirtualnego IEC Bus** (podobnie jak w Vice lub Hoxs64), do którego SDI i emulowana stacja 1541 mogą się podłączać.
